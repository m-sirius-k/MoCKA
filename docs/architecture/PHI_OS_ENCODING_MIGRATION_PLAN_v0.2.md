### 0.1 v0.1 からの訂正

**訂正前(v0.1 第4.3節)**: 作業3(risk_engine.py:147の列保全)のみでもD-4のデータ破壊は止まる。

**訂正後(実測)**: 条項E-6の文言どおり"入力に存在した列をそのまま保全する"方式で
実装した場合、event_idの値は保全される。空文字にはならない。

実測値(隔離サンドボックス、入力=現物events.csvのコピー):

| 方式 | 書き戻し後のevent_id(先頭3行) | 全132行の保全 | 列数 | `row.get("event_id","")` |
|------|------------------------------|---------------|------|--------------------------|
| 現行(FIELDNAMES射影) | `N/A` `N/A` `N/A` | 破壊 | 23 | `""` |
| Stage 1a候補(列保全) | `E20260616_061` `E20260616_062` `E20260616_063` | **保全** | 23 | `""` |

出力先頭バイトは `EF BB BF 65 76 65 6E 74 5F 69 64`(BOM + `event_id`)であり、BOMは維持される。
`row.get("event_id","")` が空文字のままであるため、重複判定(risk_engine.py:132)は
常時成立し続け、**D-5の遮蔽は維持される**。

すなわち Stage 1a 単独で、以下が同時に成立する。

- データ破壊の停止(event_id 全132行の保全)
- 露出窓の非解放(INC生成は抑止されたまま)

本訂正は(c')の評価を上方に変えるものであり、DC_20260731_004 の裁定を弱めない。

## 4. Stage 1着手ゲート(裁定済み)

DC_20260731_004 により **(c') 分割で担保** が採択された。

| 選択肢 | 結果 | 却下理由(要約) |
|--------|------|----------------|
| (a) 運用で担保 | 却下 | 運用ルールは人・自動ジョブのミスで破られうる。制度設計改善のプロジェクトで運用依存の対策を主とすべきでない |
| (b) 順序で担保 | 却下 | 別Decisionとして分離したRC-AとRC-Bを実装順序で再結合してしまう |
| (c) 分割で担保 | **採択(ただし(c')へ細分化)** | 監査で確定した依存関係の逆順をたどる。目的の異なる変更を分離できる |

### 4.1 (c')が3目的を同時に満たす機序

```
Stage 1a  コード変更のみ。BOMは残る
   -> event_id は保全される(実測)         ... データ破壊を止める
   -> row.get("event_id","") は "" のまま
   -> 重複判定が常時成立                    ... 露出窓を開けない
   -> INC生成は0件で維持

Stage 1b  コード変更のみ。データ不変        ... 遮蔽は維持

Stage 1c  作業なし。RC-B最小実装を待つ      ... D-1(承認ゲート)が入る

Stage 1d  正規化。ここで初めて遮蔽が解除    ... 承認ゲート通過後の運用開始
   -> しかし D-1 は既に是正済み
   -> 未承認INCは公開されない
```

RC-A(本計画)と RC-B(State Model)は、Stage 1c の解除条件で接続するのみであり、
実装そのものは独立して進められる。DC_20260731_002 / DC_20260731_003 の分離は維持される。

## 6. ロールバック計画(実装開始条件)

DC_20260731_004 が実装開始条件として要求する3項目。

### 6.1 前提: git はデータのロールバックに使えない

| 対象 | git追跡 | ロールバック手段 |
|------|---------|------------------|
| tools/mocka_risk_engine.py | **追跡あり** | git によるコード差分の revert |
| interface/db_helper.py | **追跡あり** | git によるコード差分の revert |
| data/events.csv | **追跡なし** | **ファイルスナップショットのみ** |

`.gitignore:2` が `data/*` を全除外しており(ホワイトリスト8件に events.csv は含まれない)、
さらに `.gitignore:15` の `*.csv` にも該当する。`git check-ignore` で確認済み。

したがって **data/events.csv の巻き戻しは git では不可能** であり、
明示的なスナップショット取得が唯一の復旧手段となる。

### 6.2 変更前のバックアップ取得

**適用対象**: Stage 1d のみ(Stage 1a / 1b はデータに触れないため不要)。

既存の運用実績に合わせる。

| 項目 | 内容 |
|------|------|
| 命名規則 | `events_backup_YYYYMMDD_HHMMSS.csv` |
| 実績 | `data/events_backup_20260401_132453.csv` / `data/events_backup_20260416_121018.csv` |
| 保存先候補 | `data/` 直下(実績あり) または `data/backups/`(ディレクトリ実在) |
| 取得方法 | バイト単位のコピー。再エンコードを行わない(BOMを含む現状をそのまま保存する) |
| 取得前の記録 | サイズ・SHA256・レコード数・先頭3バイト を控える |

**必須**: バックアップはバイト単位コピーとする。Python の csv 経由での書き出しは
改行・クォート表現を正規化しうるため、バックアップ手段として用いない。

### 6.3 正規化失敗時の復旧手順

Stage 1d の正規化が失敗した場合。

1. 直ちに tools/mocka_risk_engine.py および data/events.csv へ書き込む処理を停止する
2. 6.2 のバックアップからバイト単位で復元する
3. 復元後に以下を照合する
   - SHA256 がバックアップ取得時と一致すること
   - レコード数が132であること
   - 先頭3バイトが `EF BB BF` であること(復元後はBOM付きに戻る)
4. mocka_write_event で失敗内容と復元結果を記録する
5. Stage を 1c へ戻す(第1節の現在地表を更新する)

**失敗の定義**: 正規化後に以下のいずれかが成立した場合を失敗とする。
- event_id 列が正規化前と一致しない
- レコード数が132でない
- 列数が23でない
- 埋め込み改行を含むフィールドの値が変化している

### 6.4 検証失敗時の巻き戻し条件

各Stageの検証(第5節)が不合格の場合。

| Stage | 巻き戻し対象 | 手順 |
|-------|--------------|------|
| 1a | tools/mocka_risk_engine.py | git によるコード revert。データは無変更のため復元不要 |
| 1b | interface/db_helper.py | 同上 |
| 1d | data/events.csv + 該当コード | 6.3 の手順。その後コードを revert |
| 2 | 対象10ファイル | git によるコード revert |

**巻き戻しを行う条件**:
- 当該Stageの完了条件(第3節)を満たさない
- 回帰試験の該当項目(第5節)が不合格
- Stage 1a / 1b において、INC が想定外に生成された(遮蔽が意図せず解除された)

**巻き戻し後の記録**: いずれの場合も mocka_write_event で以下を記録する。
Stage名 / 巻き戻しの理由 / 実測値 / 巻き戻し後の検証結果。

### 6.5 実装開始条件の充足状況

| 条件 | 状況 |
|------|------|
| 変更前のバックアップ取得 | 6.2 で文書化 |
| 正規化失敗時の復旧手順 | 6.3 で文書化 |
