## 1. 現行状態モデルと不足点

### 1.1 現行に状態は存在しない

現行の docs/incidents/INC-*.md には、状態を表すフィールドが存在しない。
状態に最も近いのは INC 生成時に書かれる散文2行である。

```
## 再発防止：        <- tools/mocka_risk_engine.py:99-100
（要分析）

## 承認：            <- tools/mocka_risk_engine.py:104-106
自動生成 / 要Claude確認
```

このうち `## 承認` は状態を表す意図で書かれているが、**読み取るコードが存在しない**。
公開判定を行う tools/mocka_restrictions.py:12-19 は当該欄を一切参照しない。

### 1.2 不足点の一覧

| # | 不足しているもの | 現行の帰結 | 対応する欠陥 |
|---|------------------|------------|--------------|
| 1 | 機械可読な状態フィールド | 状態を判定できない | D-1 |
| 2 | 公開可否を決める事前条件 | 任意のINCが公開される | D-1 |
| 3 | 状態遷移の順序強制 | 分析前のINCが公開される | D-2 |
| 4 | 状態が保証する成果物の定義 | 再発防止情報の所在が生産者と消費者で食い違う | D-3 |
| 5 | 遷移の実行主体の区別 | 人間の判断を経ずに公開が進む | D-1 |
| 6 | 遷移の記録 | いつ誰が公開可としたか追跡できない | (追跡性) |

### 1.3 現行の書式不一致(実測)

状態を `## 承認` 欄の文字列から判定する方式を採る場合、既存INCの書式が一貫していない。

| ファイル | 記述 |
|----------|------|
| INC-20260401-001.md | `## 承認：Claude Sonnet 4.6 / 2026-04-01`(同一行) |
| INC-20260401-002.md | `## 承認：` の次行に `自動生成 / 要Claude確認`(別行) |
| INCIDENT_TEMPLATE.md | `## 承認：` のみ(空) |

|------|--------------------|------------------------|------------------|

### 2.1 遷移と現行処理の対応

| 遷移 | 現行の対応 | 状態 |
|------|------------|------|
| T1 `DETECTED -> ANALYZED` | tools/mocka_5w1h.py の実行 | 処理は存在するが、状態遷移として記録されない |
| T2 `ANALYZED -> APPROVED` | **なし** | 未実装 |
| T3 `ANALYZED -> REJECTED` | **なし** | 未実装 |
| T4 `APPROVED -> PUBLISHED` | tools/mocka_restrictions.py の実行 | 処理は存在するが、事前条件を持たない |
| T5 `-> CLOSED` | **なし** | 未実装 |

### 2.2 現行の実行順序との差

現行は tools/mocka_risk_engine.py:154-159 により以下の順で走る。

```

```

状態モデルが要求する順序は `T1 -> T2 -> T4` であり、現行は T4 が T1 より前にある。
これが D-2 の実体である。

## 3. 自動処理可能範囲

| 対象 | 自動可否 | 根拠 |
|------|----------|------|
| 検知からのINC生成(`DETECTED` の付与) | **自動可** | 判断を含まない。現行の auto_generate_incident() 相当 |
| T1 `DETECTED -> ANALYZED` | **自動可** | 分析の生成は現行の5W1Hエンジンが担う。DC_20260731_003 が `ANALYZED` への遷移の自動を許容している |
| T4 `APPROVED -> PUBLISHED` | **自動可** | 承認済みのものを反映する作業であり、判断を含まない |
| 遷移の記録(S-4) | **自動可** | 記録は判断ではない |
| 状態の読み取り・検証 | **自動可** | 判定基準が明文化されていれば機械が確認できる |

### 3.1 自動化してはならないもの

DC_20260731_003 の設計前提および条項 S-1 により、以下は自動化の対象外である。

- T2 `ANALYZED -> APPROVED`
- T3 `ANALYZED -> REJECTED`
- T5 `-> CLOSED`

"分析の生成"と"その分析を公開してよいという判断"は別の行為である。
前者の自動化は許容し、後者は許容しない。

## 4. Human Gate 対象範囲

| 遷移 | 人間が行うこと | 機械が行ってよいこと |
|------|----------------|----------------------|
| T2 `ANALYZED -> APPROVED` | 公開可の判断と、その記録の指示 | 事前条件(状態が `ANALYZED` であること)の確認、遷移の記録 |
| T3 `ANALYZED -> REJECTED` | 公開不可の判断 | 同上 |
| T5 `-> CLOSED` | 終結の判断 | 同上 |

### 4.1 境界の明確化

機械が行ってよいのは"人間が下した判断を、事前条件に照らして受理し記録すること"までである。
事前条件の充足をもって機械が判断を代行してはならない。

例: 状態が `ANALYZED` であり、再発防止情報が所定位置に存在し、パターンIDが割り当てられて
いたとしても、それらは `APPROVED` への遷移条件を満たすだけであって、遷移そのものを
機械が実行してよい根拠にはならない。

### 4.2 未確定

人間がどのインタフェースで承認を与えるかは未確定である
(INC_LIFECYCLE_STATE_MODEL_v0.1.md 第6節6)。

## 5. 実装時の変更対象候補

### 5.1 最小実装(Stage 1c の解除条件)

Stage 1c の目的は**露出窓を閉じること**である。露出窓とは"未承認のINCが
GPT_RESTRICTIONS.md へ自動的に掲載される"状態を指す。これを閉じるために必要な最小構成は
以下3点である。

| # | 実装項目 | 対象 | 条項 |
|---|----------|------|------|
| M-1 | 状態フィールドの保持 | 保持場所は未確定(第7節1) | - |
| M-2 | INC生成時に `DETECTED` を付与 | tools/mocka_risk_engine.py:75-111 `auto_generate_incident()` | - |
| M-3 | 公開の事前条件を `APPROVED` に限定 | **tools/mocka_restrictions.py:12-19** | S-2 |

M-3 が本質である。**公開判定を行う箇所はコード全体で1箇所しか存在しない**ことを確認した。

- GPT_RESTRICTIONS.md を書き込むコードは tools/mocka_restrictions.py:52-53 のみ
  (`.py` 全走査で他に書込箇所なし。gateway/adapter_gpt.py:249 と AI_BOOT_HUB.md は参照側)
- 公開対象を選別する箇所は tools/mocka_restrictions.py:12-19 の抽出ループのみ

したがって公開ゲートの実装面は1ファイル1箇所に閉じる。

加えて、T2 を人間に限定する条項 S-1 は、M-1 の状態を人間しか `APPROVED` に
書き換えられないようにすることで成立する。機械が `APPROVED` を書く経路を作らないことが
実装上の要件となる。

### 5.2 最小実装で解消される欠陥と、残る欠陥

| 欠陥 | 最小実装後の状態 | 説明 |
|------|------------------|------|
| D-1 承認状態確認分岐の不存在 | **解消** | M-3 により公開の事前条件が成立する |
| D-2 生成順序逆転 | **実害が消える(構造は残る)** | 起動順序は変わらないが、`APPROVED` でないINCは公開されないため、分析前の内容が公開されることはなくなる |
| D-3 抽出範囲不足 | **残る** | 承認済みINCを公開する際、抽出範囲は依然 `## 再発防止` 欄に限定される。人間が当該欄を埋めていなければ `（要分析）` が公開されうる |

**重要**: 最小実装は露出窓(未承認の自動公開)を閉じるが、D-3 は閉じない。
D-3 の解消には条項 S-3(ANALYZED の成果物契約)が必要であり、これは完全実装の範囲である。
