## 対象1: 決済導線(CTA → Stripe)の復旧

### 確定事実
- ブラウザ実機確認(`E20260709_7361161464514`)により、Pro/One「アップグレード」ボタンの`href="#cta"`がページ内に存在しないデッドリンクであることを確認。クリックしても遷移せず、Stripe関連のネットワーク通信は0件。
- 一方、決済**基盤**自体(Stripeプロダクト・Webhook・Cloudflare Worker)は2026-06-01時点で稼働確認済み(`E20260601_062`「Orchestra課金パイプライン全通復活」)。
- 2026-06-03時点で、Stripe本番Payment LinkのURL(Pro=`3cI8wP...`、One/Launch=`aFa5kD...`)が一度`orchestra_lp_content.html`へ差し替えられた記録がある(`E20260603_171`)。その後、v2/v3/v4/5言語版など複数回のLP再生成、および2026-06-30の緊急PHPバグ修正(`page-orchestra.php`直接編集)を経ており、いずれかの時点で正しいURLが失われ`#cta`のプレースホルダーへ戻った可能性が高い。

### 仮説(未検証)
バックエンド(決済処理・ライセンス発行)は生きているが、フロントエンド(LPのボタンリンク)だけが最新の正しいStripe Payment Link URLを反映していない、という「表示層のみの欠落」である可能性が高い。

### 提案する調査・修正手順
1. Stripe Dashboard(きむら博士アクセス)で、Orchestra Pro/One(Launch Edition)の現行有効なPayment Link URLを確認・取得する(`E20260603_171`記載のURLが現在も有効か要確認。無効な場合は新規発行)。
2. SSH経由(要博士承認・または博士による直接実施)で`wp-content/themes/blocksy/page-orchestra.php`(または該当ページのWordPress投稿本文)を取得し、現在の`#cta`該当箇所を特定する。
3. `#cta`を手順1で確認した正しいStripe Payment Link URLへ置換する。
4. 変更前バックアップ取得(2026-06-30の手順に倣う: `.bak`保存)。
5. ブラウザ実機で再度クリック確認(Stripe Checkoutページが実際に開くこと、金額・商品名が正しいことを確認)。
6. CHANGE_START/CHANGE_DONE記録、UTF-8検証。

## 対象2: /mini-mocka/ と /mini-mocka-2/ の公開経路整理

### 確定事実
- ブラウザ実機確認により、`https://mocka.nsjp.org/mini-mocka/orchestra/`へのアクセスが`https://mocka.nsjp.org/mini-mocka-2/orchestra/`へ遷移することを確認(`E20260709_7361161464514`)。
- 原因は2026-06-30時点で判明していた「wp_setup.shの二重実行による-2サフィックス重複ページ」(`E20260630_3197185087cb6`)と同一事象である可能性が高いが、断定はしない(R01裁定通り、301/302設定・WordPress設定・リバースプロキシ・キャッシュのいずれが原因かは未確認)。
- 本事象は2026-06-30時点で「低優先」の別TODO(`TODO_WP_DUPLICATE_PAGES_CLEANUP`)として分離されていたが、今回の実機確認により実際のユーザー導線に現在も影響していることが判明したため、優先度の再評価が必要。

### 提案する調査・修正手順
1. WP-CLI経由(SSH)で`/mini-mocka/`系と`/mini-mocka-2/`系、両方のページ一覧・投稿ステータス(publish/draft)・parent関係を取得する。
2. どちらが「正本」として意図されていたか(TODO_221のタイトル上は`/mini-mocka/`)を確認したうえで、どちらを正式な公開経路とするかをHuman Gateで裁定する。
3. リダイレクトの実体(.htaccess、WordPressのredirectプラグイン、テーマ側のtemplate_redirectフック等)を特定する。
4. 非正本側の扱い(301リダイレクト設定 or 削除)を決定・実施する。
5. 内部リンク(メニュー・他ページからの参照)が正本パスを指しているか確認する。
6. ブラウザ実機で再検証する。

## 対象3: Console SyntaxErrorの原因調査と影響評価

### 確定事実
- ブラウザ実機確認で`https://mocka.nsjp.org/mini-mocka-2/orchestra/:669:1335`にて「SyntaxError: Invalid or unexpected token」を検出(`E20260709_7361161464514`)。
- 本ページ自体のインラインスクリプト内で発生しており、外部プラグイン(wordfence等、別途検出)とは異なる。
- このエラーが対象1(決済導線欠落)の直接原因か、無関係な別の不具合かは未確定(R01裁定通り、因果関係は未確定として扱う)。

### 提案する調査・修正手順
1. SSH経由でページソース(HTML出力、およびpage-orchestra.php等のテンプレートファイル)を取得し、ブラウザ上の行番号(669行1335列、レンダリング後のHTML基準)に対応する箇所を特定する。
2. 該当スクリプトの構文誤りを特定する(6/30の`chr()`連結バグと同種のPHP8非互換コードが混入している可能性を優先的に確認する)。
3. 修正前にバックアップを取得する。
4. 構文を修正する。
5. ブラウザ実機でConsole Errorが解消したことを確認する。
6. 修正後、対象1(決済導線)の挙動に変化がないか再確認する(このエラーが対象1と無関係であることが判明した場合は、その旨を記録し完了とする)。

## 実施順序の提案

対象3(SyntaxError調査)を最初に行うことを推奨する。理由: 対象1の根本原因診断(表示層のみの欠落か、JS実行エラーによる副次的な導線破壊か)を先に切り分けることで、対象1の修正方針(単純なURL置換で足りるか、JS修正も必要か)がより正確に決まるため。対象2(重複ページ整理)は対象1・3とは独立して並行調査可能。
