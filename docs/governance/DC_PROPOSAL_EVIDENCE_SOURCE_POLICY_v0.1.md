## 1. 背景

2026-07-30、Option C（PHL Stage 1 Runner）関連のTask 1-4（JARVIS Integration Traceability Audit等）の
指示を受けた際、対象となる設計文書23件が本セッション（Cloud checkout）から一切参照できないことが判明した。
一方で、それら文書のCHANGE_DONE記録はEvent Ledgerに存在し、Decision Ledger（DC_20260730_010）にも
Option C採用確定として記録されていた。

つまり、**同一の作業について、Ledgerには記録があるが実ファイルは無い**という状態である。この状況で
Ledger要約だけを根拠に監査を進めれば、要約からの推測補完という、DC_20260729_001およびDC_20260730_009が
明確に禁じた行為に該当する。

この経験から、複数の証拠源が食い違う、または一方しか参照できない場合に、どれを優先するかを事前に
定めておく必要が確認された。

## 2. 現状の課題

### 2.1 既存ルールの粒度

DC_20260730_009は既に確認順序を定めている。

```
(1) 現在の会話履歴
(2) リポジトリ内の実ファイル（一次証拠）
(3) Decision Ledger
(4) Event Ledger
(5) その他の履歴
```

このルール自体は妥当に機能した（本件でも、この順序に従った結果として(2)の不在を検知できた）。ただし、
実運用で以下の粒度不足が明らかになった。

- (2)（リポジトリ内の実ファイル）が、**どのリポジトリ**を指すのかが不明確。本件では、Local Windows環境の
  作業ツリー・Cloud checkout・GitHub上のブランチという3つの候補があり、それぞれ内容が異なっていた。
- git commit済みのファイルと、未コミットの作業ツリー上のファイルが、同じ(2)に含まれている。両者は
  検証可能性が根本的に異なる（前者はhash・timestamp・署名で固定され後から独立検証できるが、後者は
  できない）。

### 2.2 別案として提示された順位案の検証結果

本セッションで別途提示された5段階の順位案（Local Repository / Git Repository / MCP取得内容 /
Decision Ledger / Event Summary）を検証した結果、以下3点の論点が確認された。

- **論点A**: （現在の会話履歴）のカテゴリが欠落している。DC_20260730_009では最優先に置かれている。
- **論点B**: Local RepositoryをGit Repositoryより上位に置いているが、この2つは（情報の新しさ）と
  （検証可能性）という異なる評価軸であり、単一の順位に統合すると目的により逆転する。
- **論点C**: （MCP取得内容）が独立した第3位のカテゴリとして置かれているが、実際にMCP経由で取得できる
  ものはDecision Ledger・Event Ledger（および essence / guidelines / todo / registry）であり、
  第4位・第5位と対象が重複している。

## 3. 提案内容

DC_20260730_009を**置き換えるのではなく、その第(2)段階を詳細化する**形での改定を提案する。

```
(1) 現在の会話履歴（本セッション内でユーザーから直接提示された事実）

(2a) Git Repository（コミット済み。hash・author・timestamp・署名により後から独立検証可能）
     -> 監査・裁定・Decision Ledger記録の根拠として使う場合は、この段階を優先する

(2b) Local Repository（作業ツリー。未コミットを含む）
     -> 最新の設計・作業状態を把握する目的では、この段階を優先する
     -> ただし正式な監査・裁定の根拠とする場合は（未検証来歴 / Unverified Provenance）の
        注記を必須とし、git commit後に正式な根拠へ置き換える

(3) Decision Ledger

(4) Event Ledger（Event Summary）

(5) その他の履歴
```

あわせて、以下を明文化する。

- （MCP取得内容）という独立カテゴリは設けない。MCP経由で取得できるものは(3)(4)またはその他の履歴に
  分類されるため、重複カテゴリを作らない（論点Cへの対応）。
- (2a)と(2b)の優先関係は固定せず、**目的（監査根拠か、最新状態把握か）によって選択する**。どちらを
  用いたかは、成果物に明記する（論点Bへの対応）。

## 4. メリット

1. **推測補完の構造的抑止**: 実ファイルが無い状態でLedger要約から本文を推測するという行為が、順位上
   明確に禁止される。今回のcontamination事故と同型の事象を、判断の余地なく止められる。
2. **既存制度との非衝突**: DC_20260730_009を置き換えず詳細化するため、2つの矛盾したルールが並存する
   事態を避けられる。
3. **監査成果物の検証可能性向上**: (2a)を根拠とした監査結果は、第三者がcommit hashから同じファイルを
   取得して再検証できる。(2b)を根拠とした場合は注記が残るため、検証可能性の差が事後に判別できる。
4. **多環境構成への対応**: MoCKAは現在、Local Windows環境・Cloud session・複数のGitHubリポジトリという
   多環境構成にあり、今後さらに増える可能性がある。どの環境の情報を根拠としたかを明示する規律は、
   環境が増えるほど価値が高まる。

## 5. 懸念点

1. **(2a)/(2b)の使い分けが運用者の判断に依存する**: （監査目的か、状態把握目的か）の切り分けが曖昧な
   ケースでは、どちらを優先すべきか迷う余地が残る。判断基準をさらに具体化するか、迷った場合は(2a)を
   選ぶという既定を置くかの検討が必要。
2. **未コミット資産の軽視リスク**: (2b)に注記義務を課すことで、Local環境にしか存在しない最新設計が
   （格下）として扱われ、結果的に参照されなくなる可能性がある。本来は同期を促すべき状況で、単に
   参照を避けるという回避行動を誘発しないか。
3. **運用コストの増加**: どの段階の証拠を使ったかを成果物ごとに明記する義務が生じるため、記述量が増える。
   小規模な確認作業にも同じ義務を課すと、実務が重くなる可能性がある。適用範囲（正式な監査・裁定に限る
   のか、日常の確認作業にも及ぶのか）の線引きが必要。
4. **本提案自体の証拠水準**: 本提案は2026-07-30の1件の事例（Option C監査）から導出されている。同型の
   事象は本セッションで既に3回（Genesis Phase、PHI-OS Integration Migration report、p-DERS）発生して
   いるとDC_20260730_009に記録があるが、いずれも本セッション内の観測であり、より長期の再発傾向による
   裏付けは得られていない。
