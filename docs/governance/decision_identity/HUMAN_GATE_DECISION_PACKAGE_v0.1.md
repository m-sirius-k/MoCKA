## 2. 問題定義

### 2-1. 事象

3つの decision_id に、系列関係を持たない別主題の記録が2件ずつ存在する。

| ID | 行 | 主題 |
|----|----|------|
| DC_20260730_001 | 184 / 193 | Evidence Level階層 / p-DERS Track A |
| DC_20260730_002 | 185 / 194 | Current Verified State / p-DERS Sound Local Approximation |
| DC_20260730_003 | 186 / 196 | PHI-OS Milestone 1 / MoCKA Governance Function G |

### 2-2. 実害

| # | 内容 | 実測 |
|---|------|------|
| 1 | MCP 経由で 3件が到達不能 | mocka_decision_get / _list は最新行のみ返却 |
| 2 | 参照の誤解決 | 11参照中 7件が意図と異なる記録に解決 |
| 3 | supersedes 連鎖の曖昧化 | 重複 ID を指す supersedes が 4行 |

データ損失なし。tools/audit (7本) と JSONL 直読では全件到達可能。
Command Center / Dashboard / 全 UI は Decision Ledger を参照していないため影響なし。

### 2-3. 根本にある構造

decision_id が単独で4役割 (一意性 / 系列性 / 状態更新 / 参照対象) を担うため、
"正当な状態更新" と "別決定の衝突" が同一の物理形式になり、機械的判別ができない。

## 4. HG-1 / HG-3 / HG-4 依存関係

### 4-1. 判断対象

| ID | 判断事項 | 目的 |
|----|---------|------|
| HG-1 | 対処方針 A/B/C/D の選択 | 発生済み3件の到達性を回復するか |
| HG-3 | decision_id 重複検査の追加可否と失敗時挙動 | 今後の発生を防ぐか |
| HG-4 | 明示 ID 指定の可否 | 今後の発生を防ぐか |

### 4-2. 依存構造

```
                    P-1
    "同一IDの複数行 (STATE_UPDATE) を認めるか"
                     |
       +-------------+-------------+
       |             |             |
     HG-3          HG-4          HG-1
       |             |             |
       +------+------+             |
              |                    |
    同一ID追記の可否に直接抵触   到達性の回復手段
              |                    |
              +--------+-----------+
                       |
          HG-1 = C または D の場合のみ
          HG-3 の選択肢が拡張される
```

### 4-3. 依存の内容

D-1: HG-3 は P-1 に従属する。単独判断できない。
     fail-closed  -> 正当な STATE_UPDATE 4件相当の追記が実行不能になる
     警告のみ      -> 再発を防げない
     条件付き許可  -> 系列判定規則が前提だが未定義 (DS-3)

D-2: HG-4 も P-1 に従属する。単独判断できない。
     _next_decision_id() は常に当日最大+1 を返す実装で既存 ID を返す経路がない。
     自動採番へ一本化すると同一 ID 追記が実行不能になる。
     ただし HG-4 は実装変更を伴わず運用規約のみで実施可能。

D-3: HG-1 は独立軸だが HG-3 の選択肢幅を規定する。
     HG-1 = C -> canonical により系列が構造化され、条件付き許可が可能になる
     HG-1 = D -> 行ID により衝突概念が消滅し、重複検査が不要化しうる
     HG-1 = A / B -> HG-3 は fail-closed か警告かの二択に留まる

### 4-4. 依存から導かれる順序制約

O-1: P-1 が HG-3 / HG-4 に先行する (D-1 / D-2)
O-2: HG-1 が HG-3 に先行しうる (D-3)。ただし HG-1 = A / B なら必須ではない
O-3: HG-4 は HG-1 / HG-3 と独立に先行実施しうる (運用規約のみで成立)

上記以外の順序 (どこまで一括で決めるか等) は依存関係からは導かれない。

## 6. Option A-D 選択時の決定事項一覧

方式の定義 (ARCHITECTURE OPTIONS MATRIX v0.1 準拠):

| 方式 | 識別モデル |
|------|-----------|
| A | decision_id 単独のまま。解決規則のみ変更 (読み取り側のみ) |
| B | (decision_id, revision) の複合キー |
| C | canonical ID を別に持ち、decision_id は別名 |
| D | 行ID + series ID で一意性と系列を分離 |

注意: 本 A/B/C/D は先行の Option Evaluation Matrix の A/B/C/D と対応が異なる。

### 6-1. 選択時に必要となる決定事項

| 決定事項 | A | B | C | D |
|---------|---|---|---|---|
| API 戻り値形式変更の承認 (get が単一 -> 複数) | 必要 | 不要 (引数追加で形式維持可) | 不要 (形式維持可) | 必要 (引数意味論の再定義) |
| schema 改訂の承認 | 不要 | 必要 (revision 追加) | 必要 (canonical 追加) | 必要 (v2 化) |
| 既存204行への移行方針の承認 | 不要 | 必要 (revision 既定値解釈) | 必要 (canonical 割当) | 必要 (行ID付与・series導出) |
| 重複7 ID の個別判定 (人による確定) | 不要 | 不要 | 必要 (COLLISION 3 / STATE_UPDATE 4 の割当) | 必要 (series 導出時、COLLISION 3件は誤導出) |
| §4 違反を未解消のまま残すことの承認 | 必要 | 不要 | 不要 | 不要 |
| 系列表現の使い分け規則の承認 | 不要 | 必要 (revision 増分 vs 新規ID) | 不要 (canonical 一致で判定) | 不要 (series ID で判定) |
| 参照体系変更の承認 (既存参照 構造化52 / 本文366) | 不要 | 不要 | 不要 | 必要 |
| 解決規則の schema 明文化 (P-2 / DR-2) | 必要 | 必要 | 必要 | 必要 |
| Integrity Ledger 同型適用の判断 (CM-7) | 不要 | 必要 | 必要 | 必要 |
| ツール定義2箇所の同時更新 (CM-6) | 必要 | 必要 | 必要 | 必要 |

### 6-2. 選択後に残る未解消の境界

| 境界 | A | B | C | D |
|------|---|---|---|---|
| DI-2 採番責任境界 | 残る | 残る | 残る | 残る |
| DI-3 違反検出時点 | 残る | 残る | 残る | 残る |

### 6-3. 各方式に固有の留意点 (優劣評価ではない)

A: 到達性は回復するが、返された複数件のどれが目的かの判断は呼び出し側 (MCP
   クライアント = AI エージェント) に移る。呼び出し側の静的列挙は不可能。

B: COLLISION は "別決定が同一 ID を取った" 状態であり、revision 増分として
   記録されると衝突が正当な版に見える可能性がある。増分か新規 ID かの判断規則が
   定義されない限り、衝突の防止機構にはならない。

C: 既存7重複 ID への canonical 割当には STATE_UPDATE / COLLISION の判定が前提。
   判定材料は実測済み (title 類似度 / approved_at 間隔が7件では完全分離) だが、
   判別規則としては未検証。割当は人による個別確認となる。

D: 衝突概念が構造的に消滅する一方、既存参照はすべて decision_id 文字列を前提と
   しており参照体系の再定義を伴う。既存204行からの series ID 導出は
   COLLISION 3件について誤った系列を生成する。
