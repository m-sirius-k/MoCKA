## 1. 現行モデルの限界

### 1-1. モデル

```
decision_id (文字列)
   |
   | 解決規則: ファイル内で最後に出現した行を採用 (last-wins)
   v
Decision Record (14フィールド / 1行)
```

[事実] `decision_id` 以外に Decision を識別するフィールドは schema に存在しない。
行 ID / 版番号 / canonical 参照 / alias はいずれも未定義。

### 1-2. 単一文字列への4役割集中

| 役割 | 保証 | 実測 |
|------|------|------|
| 一意性 | なし | 204行 / 197 distinct / 重複 7 ID (一意率 96.4%)。書込時検査なし |
| 系列性 | なし | 専用フィールドなし。supersedes 15/204、superseded_by 0/204、status=Superseded 1/204 |
| 状態更新 | 一意性と識別不能 | STATE_UPDATE (4 ID) と COLLISION (3 ID) が同一の物理形式 |
| 参照対象 | なし (last-wins 解決) | related_documents 内 52件 / 本文中 366件。参照される distinct ID 122 のうち 6 が重複 ID |

### 1-3. 限界の構造

[考察] 現行モデルの限界は"重複が起きたこと"ではなく、次の3点にある。

L-1. 一意性と系列性が同一の文字列に載っている
  同一 ID の複数行が"正当な状態更新"と"別決定の衝突"の両方を表現しうる。
  物理形式が同一のため、機械的判別が原理的に不可能。

L-2. 解決規則が schema に規定されていない
  last-wins は実装 (mocka_mcp_server.py:1036 / 1045、adapter.py:27-44) と docstring
  にのみ存在し、DECISION_LEDGER_SCHEMA_v1.md には解決規則の記述がない。
  すなわち"どの行が正か"は仕様ではなく実装の性質である。

L-3. 参照が型付けされていない
  Decision 間参照の専用フィールドがなく、構造化欄 (related_documents、本来は文書欄)
  と自由文の双方に散在する。参照形式が未定義のため、dangling 参照の有無すら
  機械的に判定できない (実測: 正規表現による抽出は DC-WP / DC-PHI 等の部分一致と
  DC_003 等の短縮形により過検出・欠落を伴う)。

[観測] L-1 は今回顕在化した。L-2 と L-3 は未顕在だが同じモデルに内在する。

### 1-4. 限界が顕在化した範囲

| 面 | 影響 |
|----|------|
| MCP mocka_decision_get / mocka_decision_list | あり (3件が到達不能、11参照中7件が誤解決) |
| governance/write_path/runtime/adapter.py | あり (同規則)。ただし未配線 |
| tools/audit/*.py (7本) / JSONL 直読 | なし (全行走査) |
| /decision/log 系 / Command Center / Dashboard / 全 HTML・JS / export | なし (Decision Ledger を参照していない) |

## 3. Option A-D の依存関係

### 3-1. 方式の定義 (ARCHITECTURE OPTIONS MATRIX v0.1 準拠)

| 方式 | 識別モデル | 変更の所在 |
|------|-----------|-----------|
| A | decision_id 単独のまま。解決規則のみ変更 | 読み取り側のみ |
| B | (decision_id, revision) の複合キー | schema + 書込 + 読み取り |
| C | canonical ID を別に持ち、decision_id は別名 | schema + 書込 + 読み取り + 解決層 |
| D | 行 ID + series ID で一意性と系列を分離 | schema + 書込 + 読み取り + 参照体系 |

注意: 本 A/B/C/D は先行の Option Evaluation Matrix の A/B/C/D と対応が異なる。
対応は ARCHITECTURE OPTIONS MATRIX v0.1 の冒頭注記を参照。

### 3-2. 未定義境界への対応関係

各方式が"解消する境界"と"解消しない境界"の対応。

| 境界 | A | B | C | D |
|------|---|---|---|---|
| DI-1 (同一性の定義) | 不変 | 部分 (組で一意) | 解消 (canonical) | 解消 (行ID) |
| DI-2 (採番責任境界) | 不変 | 不変 | 不変 | 不変 |
| DI-3 (違反検出時点) | 不変 | 不変 | 不変 | 不変 |
| DS-1 (系列の定義) | 不変 | 部分 | 解消 | 解消 |
| DS-3 (系列と衝突の判別) | 不変 | 部分 | 解消 | 解消 |
| DR-2 (解決規則の正本性) | 要明文化 | 要明文化 | 要明文化 | 要明文化 |
| DRF-1 (参照専用フィールド) | 不変 | 不変 | 不変 | 要再定義 |
| DRF-5 (重複IDへの参照) | 呼び出し側へ移譲 | 解消 | 解消 | 解消 |

[考察] DI-2 / DI-3 はいずれの方式でも解消しない。
これらは識別モデルではなく採番・検証の責任配分の問題であり、方式選択と独立である。

### 3-3. 方式間の順序依存

[考察] 方式そのものに順序依存はない (A-D は排他的選択)。
ただし採用後の実施可能性に次の依存がある。

```
   C を採る場合
        |
        +--> 系列表現の手段 (canonical) が新設される
        |         |
        |         +--> CM-1 の"条件付き許可"が実装可能になる
        |
   D を採る場合
        |
        +--> 行 ID により衝突概念が消滅
                  |
                  +--> CM-1 の重複検査そのものが不要化しうる

   A / B を採る場合
        |
        +--> 系列判定規則は未定義のまま
                  |
                  +--> CM-1 は fail-closed か警告かの二択に留まる
```

## 4. 判断順序

### 4-1. HG-1 と HG-3 / HG-4 の依存関係

[事実] 3判断の対象。

| ID | 判断事項 | 目的 |
|----|---------|------|
| HG-1 | 対処方針 (A/B/C/D) の選択 | 既に発生した3件の到達性を回復するか |
| HG-3 | decision_id 重複検査の追加可否と失敗時挙動 | 今後の発生を防ぐか |
| HG-4 | 明示 ID 指定の可否 | 今後の発生を防ぐか |

[考察] 依存構造。

```
              [共通制約]
   "STATE_UPDATE (同一IDでの正当な追記) を維持するか"
                    |
      +-------------+-------------+
      |             |             |
    HG-3          HG-4          HG-1
      |             |             |
      +------+------+             |
             |                    |
   両者とも同一IDでの追記      到達性の回復手段
   可否に直接抵触              (独立軸)
             |                    |
             +--------+-----------+
                      |
          HG-1 = C または D の場合のみ
          HG-3 の選択肢が"条件付き許可"へ広がる
```

依存の内容:

D-1. HG-3 は単独判断できない
  [事実] 現在の重複7 ID のうち4件は運用上意図された STATE_UPDATE である。
  fail-closed を採ると正当な状態更新の追記が実行不能になる。
  警告のみを採ると再発を防げない。
  条件付き許可を採るには系列判定規則の定義が前提となるが、規則は未定義 (DS-3)。
  したがって HG-3 は"STATE_UPDATE を維持するか"の決定に従属する。

D-2. HG-4 も単独判断できない
  [事実] 自動採番 _next_decision_id() は常に"当日最大値+1"を返す実装であり、
  既存 ID を返す経路がない。明示指定を禁止して自動採番へ一本化すると、
  同一 ID での追記そのものが実行不能になる。
  ただし HG-4 は実装変更を伴わず運用規約のみで実施可能という点で HG-3 と異なる。

D-3. HG-1 は独立軸だが HG-3 の選択肢幅を規定する
  [考察] HG-1 = C の場合、canonical により系列が構造的に表現されるため、
  HG-3 の"条件付き許可"が実装可能になる。
  HG-1 = D の場合、行 ID により衝突概念が消滅するため、
  HG-3 の重複検査そのものが不要化しうる。
  HG-1 = A / B の場合、HG-3 の制約は現状のまま (二択に留まる)。

### 4-2. 依存から導かれる順序制約

[考察] 以下は依存関係から機械的に導かれる制約であり、優先度の主張ではない。

順序制約 O-1: 共通制約 (STATE_UPDATE を維持するか) が HG-3 / HG-4 に先行する
  理由: D-1 / D-2 のとおり、両者ともこの決定に従属する。

順序制約 O-2: HG-1 が HG-3 に先行しうる
  理由: D-3 のとおり、HG-1 の帰結が HG-3 の選択肢集合を変える。
  ただし HG-1 = A / B を選ぶ場合、HG-3 の選択肢は変わらないため、
  この順序は必須ではない。

順序制約 O-3: HG-4 は HG-1 / HG-3 と独立に先行実施しうる
  理由: 運用規約のみで成立し、実装変更を伴わない。
  ただし共通制約 (O-1) には従属する。

[考察] 順序制約に該当しない部分 (どれを先に議論するか、どこまで一括で決めるか) は
依存関係からは導かれない。それは Human Gate の判断領域である。

### 4-3. CM-1 から CM-7 の優先順位

[事実] CM 項目は方式選択と独立に決定を要する共通事項である。

| # | 事項 | 現状 |
|---|------|------|
| CM-1 | 書込時の ID 検査を追加するか、fail-closed か警告か | 検査未実装 (mocka_mcp_server.py:976-985) |
| CM-2 | decision_id の明示指定を許容するか | 規定なし。運用規約のみで対処可能 |
| CM-3 | 採番責任境界 (自動採番と呼び出し側のどちらが負うか) | 未定義 |
| CM-4 | 第2書込経路 (SealGovernanceGate、DC_{execution_id}、実績0件) の位置づけ | 未定義 |
| CM-5 | §7 の superseded_by 更新規定と append-only の不整合 | 規定と実装が不整合 (0/204) |
| CM-6 | ツール定義の2箇所重複 (472-474 / 1215-1217) の解消 | いずれの方式でも両方の更新が必要 |
| CM-7 | Integrity Ledger への同型適用の要否 | 5章参照 |

[考察] 依存関係から導かれる階層。優先度の主張ではなく、
"どれが他のどれの前提になるか"の整理である。

階層1 (他の CM の前提になるもの):
  CM-3 採番責任境界
    CM-1 と CM-2 は、いずれも"誰が採番の正しさに責任を負うか"が決まらないと
    実装先・規約先を決められない。CM-3 は両者の前提である。
  CM-5 superseded_by 設計
    HG-1 の B / C / D はいずれも状態更新の表現方法に触れる。CM-5 が未解決のまま
    新しい系列表現を導入すると、系列表現が2系統併存する。

階層2 (階層1に従属するもの):
  CM-1 ID 検査 (CM-3 に従属、かつ HG-1 の帰結に従属)
  CM-2 明示指定可否 (CM-3 に従属)

階層3 (他に従属しないが、実施時に必ず伴うもの):
  CM-6 ツール定義重複 (HG-1 / CM-1 のいずれかを実施する場合、必ず両箇所の更新を伴う)
  CM-4 第2書込経路 (実績0件のため緊急性はないが、schema 適合の観点で独立に判断可能)

階層4 (波及確認):
  CM-7 Integrity Ledger (5章参照)

[考察] 階層内の順序は依存関係からは導かれない。

### 5-2. 波及確認の要否

[考察] 事実に基づく整理。

(1) 現時点の実害: なし
  Integrity Ledger の重複はすべて STATE_UPDATE であり、last-wins 解決は
  意図どおりに機能している。Decision 側で観測された"別主題の遮蔽""参照の誤解決"に
  相当する事象は Integrity 側では検出されなかった。

(2) 構造的脆弱性: 共有している
  classification_id も単一文字列で一意性・系列性・状態更新・参照対象を担っており、
  書込時の重複検査も存在しない。Decision 側と同じ条件下では同じ事象が起こりうる。

(3) 波及確認が必要になる条件
  HG-1 = A の場合: 波及なし。Decision 側の読み取り変更のみで完結する。
  HG-1 = B / C / D の場合: schema にフィールドが追加されるため、
    Integrity Ledger にも同型を適用するか否かの判断が発生する。
    適用しない場合、2つの Ledger が異なる識別モデルを持つ状態になる。
  CM-1 を実施する場合: 検査を Integrity 側にも適用するかの判断が発生する。
    適用する場合、IC 側の STATE_UPDATE 3件が fail-closed の影響を受ける。

(4) 結論
  [事実] 波及確認は"必要か否か"ではなく"未実施"である。
  現時点で Integrity 側に実害はないが、HG-1 が A 以外である場合、
  または CM-1 を実施する場合には、判断範囲に Integrity Ledger が含まれる。

## 6. 判断前に固定すべき設計原則

[考察] 以下は"原則の内容"ではなく"値を確定しておく必要のある論点"の列挙である。
いずれについても本文書は選択肢を示すのみで、採用を提案しない。

### P-1. 同一 ID の複数行を認めるか

現状: 認めている (STATE_UPDATE 4 ID / 8行が該当)。schema §4 は重複を禁じるが実装強制なし。
