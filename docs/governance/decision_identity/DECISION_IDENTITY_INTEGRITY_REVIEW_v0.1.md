## 1. Decision Identity Current Model v0.1

### 1-1. 現在モデル

```
decision_id (文字列)
   |
   | 解決規則: ファイル内で最後に出現した行を採用 (last-wins)
   v
Decision Record (14フィールドの1行)
```

[事実] 中間層 (系列 ID・リビジョン番号・canonical 参照・alias) は存在しない。
decision_id 以外に Decision を識別するフィールドは schema に定義されていない。

### 1-2. 4つの役割の分離評価

decision_id は現在4つの異なる役割を単独で担っている。

#### (1) 一意性 — 保証なし

| 項目 | 実測 |
|------|------|
| 総行数 | 204 |
| distinct decision_id | 197 |
| 重複 ID | 7 (一意率 96.4%) |
| 実装上の重複検査 | なし |
| schema 上の規定 | §4 重複禁止・欠番可 |

[考察] 一意性は schema の文言上の要求であり、実装上の強制点を持たない。

#### (2) 系列性 — 暗黙表現・明示フィールドなし

[事実] 同一決定の系列は同一 decision_id で行を追記することによってのみ表現される。

| 系列表現の手段 | 使用状況 |
|---------------|---------|
| 同一 ID での追記 | 7 ID (うち系列関係あり 4、なし 3) |
| supersedes に自 ID を指定 | 1行のみ (DC_20260712_008) |
| status = Superseded | 1行のみ |
| superseded_by | 0行 (全204行で非 null なし) |

[考察] いずれも任意かつ低頻度で、系列の有無を機械的に判定できない。

#### (3) 状態更新 — 一意性と識別不能

[事実] 状態更新と採番衝突は、ともに同一 decision_id の複数行という同一の物理形式を
とる。

[考察] これが本問題の構造的中核である。

#### (4) 参照対象 — 文字列参照のみ、解決は last-wins

| 参照形態 | 件数 |
|---------|------|
| related_documents 内の DC 参照 | 52件 (distinct 36) |
| 本文内の DC 参照 | 366件 (distinct 111) |
| 参照されている distinct ID | 122 |
| うち重複 ID (曖昧に解決される) | 6 |
| supersedes が重複 ID を指す行 | 4行 (line 67 / 121 / 123 / 185) |

[観測] 参照文字列には短縮形も存在する (DC_003 3件 / DC_005 3件 / DC_019 3件 /
DC_004 2件 等)。正規化規則は定義されていない。

### 1-3. 役割集中の要約

| 役割 | 担い手 | 保証 | 判別可能性 |
|------|--------|------|-----------|
| 一意性 | decision_id | なし (96.4%) | - |
| 系列性 | decision_id (同一値の追記) | なし | 不可 |
| 状態更新 | decision_id + 任意の supersedes/status | なし | 不可 |
| 参照対象 | decision_id 文字列 | なし (last-wins) | 不可 |

[考察] 4つの役割がすべて単一の文字列に集約されており、いずれか1つが破れると他の3つも
同時に影響を受ける構造である。


### 3-2. 単独判断可能性の評価

HG-3 (重複検査追加) — 単独判断は不可

[事実] 現在の重複 7 ID のうち 4件は運用上意図された STATE_UPDATE である。

| 実装案 | STATE_UPDATE への影響 |
|--------|----------------------|
| fail-closed | 正当な状態更新 4件相当の追記が実行不能になる |
| 警告のみ | 再発を防げない |
| 条件付き許可 | 正当な追記を機械が判定する規則が必要 (現在は存在しない) |

HG-4 (明示 ID 指定禁止) — 単独判断は不可

[事実] 自動採番 `_next_decision_id()` は常に当日最大値+1 を返す実装であり、
既存 ID を返す経路がない。明示指定を禁止して自動採番へ一本化すると、同一 ID での
追記そのものが実行不能になる。

[事実] ただし HG-4 は実装変更を伴わずに運用規約のみで実施可能という点で HG-3 と
異なる。

HG-1 (対処方針) — 独立軸だが相互作用あり

| 組み合わせ | 相互作用 |
|-----------|---------|
| HG-1=C (Alias/Canonical) | 系列表現の手段が新設され、HG-3 の条件付き許可が実装可能になる |
| HG-1=B (全件返却) | 重複が可視化されるが系列判定は与えられない |
| HG-1=A/D | HG-3/HG-4 の制約は現状のまま |

[考察] HG-1 が C の場合のみ、HG-3 の選択肢が広がる。この順序依存が依存関係上の要点で
ある。

### 3-3. STATE_UPDATE を維持する場合に必要となる識別方式

[考察] 以下は必要となる論点であり、採用の推奨ではない。

| 分離方式 | 必要になるもの | 現状での不在 |

| リビジョン番号を併用 | revision フィールド、採番規則 | revision は存在しない |
| supersedes/superseded_by を系列表現の正本とする | 必須化、superseded_by の更新方法 | supersedes 15/204、superseded_by 0/204 |
| 内容ベースの系列判定規則 | 判定規則の定義と閾値 | 規則は存在しない |
