## 第1部: 現状把握

### 1.1 なぜ判定基準を先に固定する必要があるか

`docs\governance\CONCEPT_AUDIT_v0.1.md`（本日先行作成）では、Registry/Ledger/Memory/Archive/Catalogの各クラスタについて「粒度が異なる」「階層が異なる」という表現で重複の有無を判定した。この判定は各クラスタを担当したサブエージェントの定性的な読み取りに基づくものであり、「何をもって粒度が異なるとするか」の基準が事前に固定されていなかった。

今回の指示は、この反省を踏まえ、本体監査（対象の実体調査）に着手する前に、判定基準そのものを固定することを求めている。基準を先に固定しない場合、判定結果が「対象を見た印象」に左右され、後から「なぜその対象は重複と判定し、こちらは階層違いと判定したのか」を説明できなくなるリスクがある（要確認: これが指示の意図と一致するかは博士に確認していないため断定しない）。

### 1.2 前提として整理済みの事実

- `CONCEPT_AUDIT_v0.1.md`第2.1節で、Ledgerクラスタに「追記型・改ざん検知証跡パターンの3〜4重並行発明疑い」が指摘されている（ledger.json / mocka_events.db+audit_trigger.py / decision_ledger.jsonl(PHI-OS) / KN_SERIES_LEDGER(実体未確認)）
- 同第2.2節で、KN-004 RegistryとMODULE_CATALOG_v1のスコープ重複疑いが指摘されている
- いずれも「一次的な仮説」「要検証」と明記されており、確定した重複認定ではない

## 第2部: 提案 — 四観点判定ルール

### 2.1 四観点の定義

| 観点 | 定義 | 「一致」とみなす基準（初稿） |
|---|---|---|
| (1) 書き込み経路 | 誰が/何がこの対象にデータを書き込むか（呼び出し元の関数・クラス・MCPツール・スクリプト） | 書き込みを行う実装主体（関数/クラス/エンドポイント）が同一である場合に「一致」とする。呼び出し方法の見た目（例: 両方ともJSON追記）が似ているだけでは一致とみなさない |
| (2) 読み取り経路 | 誰が/何がこの対象からデータを読み取るか | 同上。読み取りを行う実装主体が同一である場合に「一致」 |
| (3) 失敗時の挙動 | データが壊れた・整合性が取れなくなった場合に何が起きるか（検知方法・エラー通知先・復旧手段の有無） | 検知メカニズムと通知/復旧の経路が同一である場合に「一致」 |
| (4) 参照元一覧 | 何がこの対象の存在・内容に依存しているか（他モジュール・他ドキュメント・他制度） | 依存元の集合が重複する場合に「一致」（完全一致でなくとも主要な依存元が重なっていれば一致寄りとする。この閾値は初稿であり運用実績で見直す） |

### 2.2 判定ロジック

```
四観点すべてが判明し、かつすべて一致
    -> 「同一パターンの重複実装」（統合検討対象）

四観点すべてが判明し、1つ以上不一致
    -> 「分離が必要、または階層が異なる」
       (不一致だった観点を必ず明記する。どの軸が違うから
        分離されるべきなのかを言語化できない分離判定は無効とする)

いずれかの観点が不明・未調査
    -> 「判定保留」
       (「不一致」とは区別する。情報不足を重複ではないことの
        根拠として使わない。逆に情報不足を重複であることの
        根拠にもしない)
```

「判定保留」を独立したステータスとして設けることが本ルールの核心である。情報が不足している状態で「たぶん別物だろう」という感覚的判断を下すことを防ぐため、四観点のうち1つでも未調査であれば機械的に「判定保留」とし、本体監査でその観点を埋めるまで結論を出さない。

### 2.3 記録フォーマット（本体監査で使用する表の型）

| 対象名 | (1)書き込み経路 | (2)読み取り経路 | (3)失敗時の挙動 | (4)参照元一覧 | 各項目の情報源 | 総合判定 |
|---|---|---|---|---|---|---|
| （記入例） | | | | | ファイルパス:行番号 | 重複実装 / 分離必要（不一致の観点） / 判定保留（不明の観点） |

### 2.4 ワークド・イグザンプル（新規調査は行わず、既存の調査結果のみを用いる）

`CONCEPT_AUDIT_v0.1.md`で「3〜4重発明疑い」とされたLedgerクラスタの4候補に、上記ルールを試験的に当てはめる。新規のファイル調査は行わず、既存ドキュメント（CONCEPT_AUDIT_v0.1.md、その元になったExplore調査結果）に記載済みの情報のみを使う。

| 対象名 | (1)書き込み経路 | (2)読み取り経路 | (3)失敗時の挙動 | (4)参照元一覧 | 総合判定 |
|---|---|---|---|---|---|
| `runtime\main\ledger.json` | schema.pyの`append_event()`（既知） | `scripts\ledger\ledger_verify.py` / `anchor_update.py`（既知） | 要確認（ledger_verify.pyがチェーン不整合を検知した際の具体的な通知先・復旧手段は未調査） | `anchor_update.py`（mocka-seal機能）、他は要確認 | **判定保留**（(3)が不明） |
| `data\mocka_events.db` + `phi_os\audit_trigger.py` | `mocka_write_event`（MCP経由）、event_gateで一元化（既知） | `mocka_search`等のMCPツール群（既知） | `audit_trigger.py`のSQLiteトリガー（`trg_detect_direct_insert`等）がaudit_violationsへ記録（既知） | Decision Policy（Decision Evidence参照元として既知）、GL7との関係は要確認 | **判定保留**（(4)が一部不明） |
| PHI-OS `decision_ledger.jsonl` | ISE内部の状態遷移コード（詳細未調査、要確認） | 同ISE内の`verify_chain()`（既知だが呼び出し元の詳細は未調査） | 要確認 | PHI-OS ISE内で完結しているか、他モジュールから参照されるかは未確認 | **判定保留**（(1)(3)(4)が不明） |
| CATEGORY_REGISTRY_v2.0が参照する「KN_SERIES_LEDGER」 | 不明（実体ファイル自体が未確認） | 不明 | 不明 | CATEGORY_REGISTRY_v2.0が「一次ソース」と記載（既知）、それ以外は不明 | **判定保留**（(1)(2)(3)が不明、実体調査が最優先） |

**このワークド・イグザンプルから導かれる結論:** 現時点の情報だけでは4観点すべてが判明している候補は一つもない。したがって、`CONCEPT_AUDIT_v0.1.md`で用いた「3〜4重発明疑い」という表現は、本ルールに照らすと正確には「判定保留（4件とも重複と断定する材料は不足している）」と言い直すべきである。これは前回の記述を訂正する意味を持つ自己修正であり、本体監査ではこの4件の(1)〜(4)を埋めることが最優先の調査項目になる。

## 第3部: 未確定事項
