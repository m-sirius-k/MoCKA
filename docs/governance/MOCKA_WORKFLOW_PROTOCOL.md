# MoCKA 開発・検証標準運用プロトコル（MOCKA-SOP-001）
**Version:** 1.0.0  
**Status:** Canonical Standard  
**Governance Principle:** Evidence-Bound Realism / Silence Prohibition Protocol  

---

## 0. 根本理念（The Prime Directives）

1. **虚偽および隠蔽の全面排除 (No Fabrication / Anti-MOCK)**
   * 検証を通過させるためだけのコード変更、存在しないファイルの登録、HEAD にないシンボルの行番号合わせ、根拠のない承認記録の作成を厳禁とする。
   * 「ファイルが存在しない」「未コミット状態（stash/WIP）に依存している」といった不都合な事実は、隠さずそのまま正しく記録・反映する。

2. **事実拘束型の動的最適化 (Evidence-Bound Optimization)**
   * 作業途中で予期せぬ障害や不一致が判明した場合、強引な完了を目指さず、判明した事実から逆算して計画（Plan）を柔軟かつ誠実に再構築する。

3. **安全域および承認境界の厳守 (Strict Authorization Boundaries)**
   * Git への書き込み（commit, push, 大規模な stash apply 等）は、影響範囲の完全評価および明確な承認（Human Gate）なしには実行しない。

---

## 1. 標準運用ライフサイクル（12 段階プロトコル）

### 【フェーズ A：設計・影響調査・着手】
* **① 原案ロードマップの作成**
  * 目的、対象資産、期待されるゴール、および前提条件を明記した初期計画を策定する。
* **② 周辺関連影響調査**
  * 読取専用のコマンドを用いて、変更が波及する依存モジュール、ファイル構造、既存の検証スクリプトへの影響範囲をあらかじめ特定する。
* **③ 具体的手順の作成（複数案の用意）**
  * 標準的な実施手順に加え、環境差分や障害発生時に備えた代替手順（フォールバックパス）を複数パターン作成する。
* **④ 着手**
  * 承認された最小範囲に限定して、作業および検証を開始する。

---

### 【フェーズ B：動的デバッグと誠実な順応（閉ループ）】
* **⑤ 不誠実な事実・エラー発見時の Plan 変更**
  * 検証中またはデバッグ中に「欠落ファイル」「行番号の不一致」「隠れた未コミット依存」等の不誠実な事実・障害が発見された場合、即座に作業を停止し、計画を変更する。
  * 失敗・エラーを隠蔽するための短絡的な処置（一括 stash apply やダミーデータ生成など）は一切行わない。
* **⑥ 最適解の組換え（動的再構築）**
  * 単純適応が不可能な場合、⑤ で蓄積された「判明した事実・制約」から逆算し、最も構造的に誠実な最適解（ステータスの PARTIAL 降格、MISSING 登録、孤立ブランチへの切り出しなど）へ計画を再構成する。
* **⑦ 周辺調査（デバッグ影響評価）**
  * 修正・再構成が既存の構造索引や他コンポーネントに与えた影響を読取専用で再確認する。

---

### 【フェーズ C：検証・完了確認】
* **⑧ 一次完了**
  * 対象範囲の修正・補正作業を完了する。
* **⑨ デバッグ（検証スクリプト実行）**
  * verify_mapping.py や verify_unified.py などの自動検証ツールを実行し、整合性を機械的にチェックする。
* **⑩ 再度周辺影響調査**
  * 修正後の最終状態で、予期せぬ破綻や派生ファイルの非同期（SYNC 不良）が発生していないか最終確認を行う。

---

### 【フェーズ D：HG 報告・承認・永続化】
* **⑪ 経緯の調査と現状把握 -> HG 報告・完了取得 (Human Gate)**
  * ここに至るすべての経緯、選択した判断、残存する既知の不整合を「事実のまま」整理し、Human Gate（人間権限）へ報告して最終完了の承認（GO/NOGO）を得る。
* **⑫ 完了宣言・イベント保存・MOCKA Memory 保存・Mapping 反映**
  * Human Gate の承認取得後、正式に完了宣言を発令する。
  * VERIFICATION_LOG.md へのイベント記録、MoCKA の永続記憶（Memory）への知見保存、および Mapping（ASSET_INDEX.json 等）への最終状態反映を完了させる。
