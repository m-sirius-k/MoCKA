## 分類体系

本DRAFTおよびTask-Iが扱う「衛星リポジトリの位置づけ」は、性質の異なる複数の軸を含む。混同を避けるため、以下のとおり軸を分離して定義する。①と②は独立軸であり、どちらか一方が正でもう一方が誤ではない。

- **①Operational State(Task-I由来)**: 現役 / 統合済み・凍結 / 将来再利用 / 保守停止。Task-I第4部が4衛星リポジトリ共通の枠組みとして支持根拠・反証を整理済み。ただし、Task-Iはこの4選択肢についてリポジトリごとの支持・反証を整理したのみで、個別リポジトリへの確定当てはめは行っていない(Task-I第5部「最終的な当てはめの決定は博士が行う」と明記)。加えてTask-I第3部では、リポジトリごとに「候補1/候補2/候補3」という複数の暫定候補が未確定のまま列挙されている。したがって①には現時点で単一の確定値が存在しない
- **②Integration Policy(本DRAFT由来)**: A=Active(コアへ統合)/ B=Frozen(凍結)/ C=Boundary-Coexist(境界明示による共存)。DECISION_RULE_LAYER_v1.0.md類型4(モジュール境界問題)の裁定語彙(統合/境界明示による共存/凍結)を、各衛星リポジトリに適用した軸。本DRAFT第1部で新たに整理した
- **③Structural Attribute(補助・現状未使用)**: 通常 / 境界保持(overlay)。「通常」は当該リポジトリが単独で完結した実装単位であることを指す。「境界保持(overlay)」は、他リポジトリの機能に薄く重なる形で存在し、境界情報自体の保持・提示を主目的とする実装であることを指す(例: 将来、複数リポジトリ間の境界を明示するための薄いラッパー実装が該当しうる)。本節は定義のみを行い、今回の4衛星裁定では適用対象なし(4リポジトリいずれも「通常」に該当し、全て②Integration Policyの枠組みで完結すると考える)

②Integration Policyは①Operational Stateの値に依存せず定義されるが、その意味解釈は①の値によって変化する(例: ①=現役×②=Boundary-Coexistは並列運用、①=保守停止×②=Boundary-Coexistは意味保持のみのアーカイブ構造、というように、同じ②の値でも①との組み合わせで解釈が異なる)。

## 第2部: Prevention不在(5番目)の裁定

観察事実(Task-Iより): MoCKAコアのREADMEに`preventive_rule_engine`(「障害の事前防止」)という項目がコア内実装として記載されているが、衛星リポジトリとしては存在しない。8段階Loopのうち5番目(Prevention)には、どの衛星リポジトリのYOU ARE HEREも割り当てられていない。

Task-Iが既に整理した診断的選択肢(なぜ担当リポジトリが不在なのかを説明する選択肢):

- 選択肢A: Preventionの機能は最初からMoCKAコア内の`preventive_rule_engine`として実装される設計であり、衛星リポジトリを持たないことは意図的な設計である
- 選択肢B: 衛星リポジトリとして独立させる計画があったが未着手であり、本来は欠落である
- 選択肢C: 他の衛星リポジトリ(例: mocka-transparencyの再発検知機能)の一部として実質的にカバーされているが、README上は明示されていない

上記A/B/Cは「なぜ不在か」を説明する診断であり、「今後どうするか」というアクションの決定ではない。前回提示された「衛星新規追加」という裁定案は、診断としてはBを前提とした上で、それに対するアクション(新規衛星リポジトリを追加する)を決定するものであり、Task-Iの選択肢の範囲を超える別の問いである。両方を分けて博士の判断を仰ぐ。

### 診断(なぜ不在か)についての支持根拠・反証

| 選択肢 | 支持根拠 | 反証 |
|---|---|---|
| A(意図的設計) | `preventive_rule_engine`が既にコア内実装として存在し、機能自体は欠落していない | 他のLoop段階(Record/Incident/Recurrence等)はいずれも専用の衛星リポジトリを持っており、5番目だけコア内実装のみという非対称性の理由が説明されていない |
| B(本来欠落) | 他の7段階すべてに衛星リポジトリが対応している中、5番目だけが対応リポジトリを持たないという非対称性がある | `preventive_rule_engine`という実装自体は既に存在しており、「欠落」と呼ぶには機能そのものは存在する |
| C(実質的にカバー) | mocka-transparencyの再発検知機能等、他の衛星リポジトリの機能が部分的にPreventionの役割を代替している可能性がある | README上でこの代替関係が明示されておらず、本ファイルの調査範囲では裏付けが取れていない(要確認) |

### アクション(診断B前提の場合、新規衛星リポジトリを追加するか)についての支持根拠・反証

| 選択肢 | 支持根拠 | 反証 |
|---|---|---|
| 新規衛星リポジトリを追加する | 本体統合(選択肢Aの延長)は本体の過密化を招く。既存衛星への分散内包(選択肢Cの延長)は機能の所在を不可視化する。独立した新規レイヤーとして明示的に追加する方が、他の7段階との対称性を保てる | 新規リポジトリの追加は、既存衛星リポジトリの位置づけ(第1部)が確定する前に行うと、後で境界の再整理が必要になる可能性がある |
| 追加しない(A/Cいずれかの診断のまま維持) | 新規リポジトリを増やすこと自体が、Decision Rule Layerが警戒する「安易な段階追加・構造追加」に類する判断を伴う | 非対称性(5番目だけ衛星リポジトリを持たない)が未解消のまま残る |

くろこ提案: 診断はB(本来欠落)、アクションは新規衛星リポジトリ追加を提案する。理由: 他の7段階すべてに対応する衛星リポジトリが存在する中、5番目だけが実装(コア内`preventive_rule_engine`)はあるがリポジトリを持たないという非対称性は、Cのように他リポジトリへの分散内包で説明するには裏付けが不足しており、Aのように意図的設計と見るには他段階との対称性の欠如を説明できない。ただし、この提案は第1部(4衛星リポジトリの位置づけ)の結論と合わせて再検討する余地がある。提案であり決定ではない。

## 第3部: Audit/Institutionalize(8番目)の二重主張の裁定

観察事実(Task-Iより): mocka-civilizationのREADMEは8番目を"Audit -> Institutionalize"とし、内部還流(全レイヤーが検証済み知見を上位に送る/原則が全レイヤーに流れ下りる)として記載。mocka-publicのREADMEも8番目を"Audit output"とし、外部公開(一般公開・第三者監査人・将来のエージェント)として記載。両者とも図中で8番目に「YOU ARE HERE」を置いているが、線形(分岐なし)で描かれている。

Task-I選択肢:

- 選択肢A: 8番目は「内部の制度化(mocka-civilization)」と「外部への公開(mocka-public)」という2つの並行した出力先を持つ意図的な設計であり、矛盾ではない。図を分岐形式に改める余地がある
- 選択肢B: 表記の重複であり、どちらか一方が本来別の番号(例: mocka-publicは9番目相当の「公開」として8番目とは別立てにする)に整理されるべきである
- 選択肢C: 現状の表記のまま許容し、対応不要とする

前回提示された「二層分離維持」という裁定案は、Task-I選択肢Aと同じ趣旨(Audit=観測とInstitutionalize=制度化を性質の異なる2層として維持する)であり、Task-Iのラベルでは選択肢Aに相当する。以降、本DRAFTではTask-I表記(A/B/C)に統一して扱う。

支持根拠・反証:

| Task-I選択肢 | 支持根拠 | 反証 |
|---|---|---|
| A(2出力先・意図的) | Audit(観測・検証)とInstitutionalize(制度化)は性質が異なる作業であり、内部還流と外部公開という別々の宛先を持つことは自然である | 現状の図はいずれも線形(分岐なし)で描かれており、意図的な分岐設計であることを示す記述は図表記からは読み取れない |
| B(番号の再整理) | 8番目という同一番号に異なる意味(内部還流/外部公開)が同居している状態は、番号体系として曖昧である | 番号の再整理はmocka-public・mocka-civilization双方のREADME変更を要する可能性があり、本裁定の範囲(位置づけの整理)を超える実装変更に踏み込む恐れがある |
| C(現状許容) | 実害が具体的に確認されていない限り、変更コストをかけない選択肢として成立する | 8番目の意味が何を指すか(観測か制度化か)が対外的に曖昧なままになる |

くろこ提案: 選択肢A(二層分離維持)を提案する。理由: AuditとInstitutionalizeは性質の異なる作業であり、統合すると両者の意味が失われる。番号の再整理(選択肢B)はREADME変更という実装作業を伴い本裁定の範囲を超えるため、現時点では性質の違いを明文化した上で両者を維持する方が影響範囲が小さい。提案であり決定ではない。
