# Decision Rule Layer v1.0

位置づけ: くろこ作業指示(2026-07-03)に基づき新規作成。Status Vocabulary裁定(Step 1)着手前の前提文書として、Task-D frameworkと同格に位置づける。REPOSITORY_STATUS_VOCABULARY_v0.1.md(Task-H)で記録した4件のStatus Vocabulary Ambiguityが、性質の異なる4種類の問題を含んでいることを踏まえ、同一の「採用/不採用」という判定語を異なる性質の問題に対して無自覚に流用しないよう、先に問題類型と裁定規則を定義する。

目的: Status Vocabulary裁定(Step 1)以降で使う判定語彙を、問題の性質ごとに使い分けるための分類枠組みを確定する。

---

## 第1部: 問題類型と裁定規則

### 類型1: 表記問題

定義: 意味は一致しているが、言語・表記ゆれのみが原因の不一致(例: EN-JP不一致)。
裁定の中身: 正規表記を1つ選び、他は「別名(alias)」として記録するだけ。意味論的判断は不要。
判定語彙: 統一/別名登録

### 類型2: 構造問題

定義: 同じ語が異なる意味段階(例: Active vs Active Development)を指しており、語彙体系そのものの粒度が曖昧。
裁定の中身: 7段階語彙のどこに位置づくか、または新規段階が必要かを判定。
判定語彙: 既存段階に統合/新規段階追加/対象外

### 類型3: 実装主張問題

定義: リポジトリ側の「実装済み」主張と、検証(CI/commit/coupling)結果が食い違う(例: execution-runtime-system)。
裁定の中身: 制度評価とは独立した「事実検証レイヤ」として保持し、Step 1の採用判定とは非連動とする。格付けや現状維持といった評価語彙は使わず、検証ログとして事実のみ記録する。
判定語彙: 検証ログ記録のみ(採用可否の対象外)

### 類型4: モジュール境界問題

定義: 同一主体が複数の独立体系を並行運用しており、どちらが正典か、あるいは共存が正しいかが未確定(例: sirius-lab二重体系)。
裁定の中身: 統合するか、意図的並行(境界明示)として制度化するかを選ぶ。所有権・スコープの問題であり、表記や実装の問題ではない。
判定語彙: 統合/境界明示による共存/凍結(TODO_390のARCHIVE層と同扱い)

## 第2部: 適用規則(必須)

- Step 1の4件のambiguityは、裁定前にまずこの4類型のどれに該当するか分類する(複数該当は主要因を1つ選ぶ)
- 同一類型内でのみ統一判定語を使う。異なる類型間で判定語を混用しない
- 類型3(実装主張問題)はStep 1〜3のいずれの採用判定にも算入しない。独立した検証ログ(VERIFICATION_LOG)として並走記録するのみで、制度採用プロセスとは非連動とする
- 類型4(モジュール境界問題)の「凍結」は判断放棄ではなく、再検討条件を明記した上での保留とする
- 類型1・2・4について、実際の採用/不採用の最終確定は博士の明示確認を経てから行う。本文書はあくまで分類枠組みの定義であり、個別裁定そのものではない(VOCABULARY_CONSTITUTION_v0.1.md「Approval(Human Gate)」節の「AIが自身の判断を自身で確定させる自動承認ループの構築禁止」に従う)
