# Reusable Governance Patterns v0.1

Status: パターン抽出と再利用可能性の評価（制度化は含まない）
Date: 2026-07-30
記録者: 執行官Claude（くろこ、Cloud session）
関連: GOVERNANCE_CANDIDATE_REVIEW_v0.1.md、および本セッション作成の監査基盤文書8件

本文書は、Option C監査で得られた知見を、特定案件から切り離した再利用可能なパターンとして抽出し、
他プロジェクト（PHI-OS、PlanningCaliber系製品、および将来の別リポジトリ）への適用可能性を評価する。

評価は楽観的な一般化を避け、各パターンが成立するための前提条件を明示する。前提条件を満たさない環境では
再利用できない旨も記載する。

---

## 1. 全パターンに共通する前提条件

以下を満たさない環境では、本文書のパターンはいずれも十分に機能しない。

- **P-1: 記録層と実体層が分離していること。** 作業の記録（Ledger、イベントログ、issue tracker等）と、
  作業の成果物（ファイル、コード）が別々に保存され、独立して失われうること。両者が常に同一トランザクション
  で更新される系では、本文書が扱う乖離そのものが発生しない。
- **P-2: 実行環境が複数存在しうること。** 単一の開発者が単一のマシンで作業する系では、環境間の乖離は
  発生しない。
- **P-3: 記録層に追記された内容が、後から独立に取得できること。** 記録が揮発する系では、乖離の検知
  そのものができない。

MoCKAはP-1からP-3をすべて満たす（events.db / Decision Ledgerと、git管理下のファイルが分離しており、
Local Windows環境・Cloud session・GitHubという複数環境が存在する）。

---

## 2. パターン一覧

### PATTERN-1: Evidence Availability Audit（証拠可用性監査）

**問題**: 監査・調査の指示を受けたが、その前提となる一次資料に到達できるかが不明。到達できないまま
作業を進めると、要約や記憶からの推測補完が混入する。

**解法**: 監査そのものに着手する前に、（何が確認でき、何が確認できず、なぜ確認できないか）を独立した
成果物として記録する。結論を出さないことを明示的な制約とする。

**再利用可能性**: **高い。** ドメイン非依存。前提P-1のみを要求する。他プロジェクトでは、Ledgerを
issue tracker・CI履歴・設計文書リポジトリ等に読み替えればそのまま適用できる。

**再利用時の注意**: （監査不能）という結論自体を成果物として認める文化が必要。監査不能の報告が
（仕事をしていない）と評価される組織では、このパターンは推測補完に負ける。

---

### PATTERN-2: Repository Divergence Detection（環境乖離の早期検知）

**問題**: 複数環境のどれを見ているかを意識せずに作業を開始し、作業完了間際に前提の不一致が発覚する。

**解法**: 継続作業を装った指示を受けた時点で、軽量な確認から順に（ブランチ / リモート到達性 / 実ファイル
実在 / 記録層の実在）を確認する定型手順を実行する。

**再利用可能性**: **高い。** ただし具体的なコマンド（git rev-parse、mocka_decision_get等）は環境
依存であり、手順の**構造**（軽い確認から重い確認へ、実体層と記録層の両方を確認する）のみが再利用対象と
なる。他プロジェクトへ持ち込む際は、コマンド部分の書き換えが必須。

**再利用時の注意**: 本パターンは（指示を受けた直後）という発火タイミングが本質である。定期実行に
置き換えると、指示と確認の間にずれが生じ、検知が遅れる。

---

### PATTERN-3: Audit Capability Matrix（監査能力マトリクス）

**問題**: ある監査タスクを、どの環境から実施すべきかの判断が、都度の勘に依存する。

**解法**: 監査項目 x 環境の表を作り、各セルを（可 / 一部可 / 不可 / 不明）で埋める。各セルの判定根拠
（実測か推定か）を併記する。

**再利用可能性**: **形式は高い。内容は再利用できない。** マトリクスという形式・（実測と推定を区別して
記載する）という規律は他プロジェクトへそのまま持ち込めるが、記載内容は環境構成に完全依存するため、
各プロジェクトで新規作成が必要。

**再利用時の注意**: セルの値は時点依存で変化する。本セッション中にも、push権限が（不可）から（可）へ
実際に変化した。マトリクスには必ず測定日を記載し、古い値を制度的事実として扱わないこと。

---

### PATTERN-4: Evidence Synchronization（証拠同期）

**問題**: 環境間の乖離が判明した後、どの経路でどう埋めるかが定まっていない。その場しのぎの貼り付けが
横行し、来歴が失われる。

**解法**: 同期単位を（コミット単位 / 文書単位）で明示的に選択し、コミット単位を第一選択とする。文書単位を
使う場合は（来歴未検証）の注記を義務づけ、後日コミットへ置き換える条件を課す。

**再利用可能性**: **中程度。** 考え方（来歴が残る経路を優先し、残らない経路には注記義務を課す）は
一般性を持つ。ただし現在の記述はCloud/Local/MCPという本件固有の3環境に密結合しており、そのままでは
他プロジェクトへ持ち込めない。抽象化（環境名を役割名へ置換する等）を経る必要がある。

**再利用時の注意**: 同期の（完了判定）を定義しないと、パターンとして機能しない。実体が存在するだけでは
不十分で、記録層の記録と時系列上矛盾しないことの確認までを完了条件に含めること。

---

### PATTERN-5: Statement-Level Classification（記述単位の確度分類）

**問題**: 文書単位で（信頼できる / できない）を判定すると、1つの文書内に確定事実と推測が混在する場合に
対応できない。特に歴史的再構成では、後知恵の因果接続が事実として混入しやすい。

**解法**: 文書単位ではなくStatement単位で確度を分類する（Confirmed / Source / Founder Narrative /
Hypothesis / Unknown / Rejected）。Unknownを推測で埋めることを明示的に禁止する。

**出典**: Genesis Phase調査統合方針（DC_20260728_006）で確立。本セッションではOption C監査側にも
実質的に適用した（AUDIT_CAPABILITY_MATRIX_v0.1.mdの（実測）と（推定）の区別がこれに相当する）。

**再利用可能性**: **最も高い。** ドメイン非依存であり、前提P-1からP-3すら要求しない。歴史的再構成・
インシデント調査・アーキテクチャ考古学（既存システムの設計意図の復元）など、証拠が不完全な調査全般に
適用できる。

**再利用時の注意**: 分類語彙は対象に応じて調整が必要（Founder Narrativeは創始者が存在する文脈固有の
語彙であり、一般のシステム調査では不要な場合がある）。分類の**粒度をStatement単位に置く**という点のみが
本質である。

---

### PATTERN-6: Proposal-Before-Ledger（記録前の提案段階）

**問題**: 制度化すべき知見が得られた際、即座に正式記録へ書き込むと、検証不足のまま義務が発生する。
一方、記録しなければ知見が失われる。

**解法**: （提案書）という中間状態を設ける。提案書には背景・課題・提案・メリット・懸念点・未解決事項を
必須項目として含め、未解決事項を空欄にしないことを条件とする。承認を経た場合のみ正式記録へ昇格させる。

**出典**: 本セッションのDC_PROPOSAL_EVIDENCE_SOURCE_POLICY_v0.1.md（きむら博士の明示指示による）。

**再利用可能性**: **高い。** ADR（Architecture Decision Record）運用を行う任意のプロジェクトへ適用
できる。ADRにproposed / accepted / supersededの状態を持たせる一般的な運用と同型だが、本パターンは
（懸念点と未解決事項を必須項目とする）点に特徴がある。

**再利用時の注意**: 提案書が承認されないまま放置されると、（提案書はあるが制度は無い）という宙吊り状態が
蓄積する。提案書には審査期限または（未審査のまま放置された場合の既定の扱い）を定めておくことが望ましい
（本セッションの提案書には未設定。改善余地として記録する）。

## 3. 他プロジェクトへの適用評価

### 3.1 PHI-OS

PHI-OSは前提P-1からP-3を満たすと推定される（Event Gate経由の記録層と、phi_os/配下の実装が分離しており、
Chrome拡張・ローカルRuntime・MoCKA本体という複数環境が存在する）。ただし本セッションからPHI-OSの
実行環境を直接観測できていないため、この推定は未検証（Unknown）である。

適用価値が高いと考えられるのは、PATTERN-5（Statement-Level Classification）とPATTERN-6
（Proposal-Before-Ledger）である。理由: PHI-OSは現在、PHI-REG-01 / PHI-REG-02という2系統の名称衝突
（MOCKA_PHI_OS_IDENTITY_AUDIT_v1で確定済み）を抱えており、さらにConcept-C（JARVIS構想）がDeferredの
まま未分類で存在する（DC_20260729_001）。このような（確度の異なる複数の設計案が併存する）状況は、
まさにPATTERN-5とPATTERN-6が対象とする問題である。

### 3.2 PlanningCaliber系製品（Relay / Orchestra / Memory等）

これらは商用製品であり、監査基盤よりも製品機能が主眼となる。PATTERN-2（Divergence Detection）は、
拡張機能の正本パス問題（extension_canonical_paths、TODO_354で確立、E20260621_378795484b70fが発端）と
同型の問題を扱っており、適用価値がある。実際、当該インシデント（野良フォルダへの誤変更が本番に反映
されない）は、本文書のPATTERN-2が検知対象とする（どの環境を見ているか意識せずに作業した）事例である。

### 3.3 適用が推奨されない場面

- 単一開発者・単一環境・小規模の作業。前提P-2を満たさず、手順のコストが便益を上回る。
- 記録層を持たないプロジェクト。前提P-1を満たさず、PATTERN-1・2・4が成立しない。

---

## 4. 本文書の限界

- 各パターンの（再利用可能性）評価は、本セッションでの1事例（Option C監査）からの導出である。複数の
  異なる案件での適用実績による裏付けは無い。
- 3.1（PHI-OSへの適用）は、PHI-OSの実行環境を本セッションから直接観測できていないため、推定に基づく。
- パターンの有効性は、適用後の結果によってのみ検証される。本文書はその検証を含まない。
