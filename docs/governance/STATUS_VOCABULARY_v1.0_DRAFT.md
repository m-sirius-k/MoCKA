## 第1部: 類型1(表記問題) - EN-JP不一致(Ambiguity-4)の正規表記選定

対象: m-sirius-k(プロフィール)README。EN版"Research Stage: Active Development"、JP版「研究開発段階」。EN版は7段階語彙のうち"Research"と"Active Development"の両方を含む複合表現であり、どちらか一方に一意に対応しない。JP版にはEN版の"Active Development"に相当する語が見当たらない。

### 選択肢

- 選択肢A: 正規表記を"Active Development"とする。EN版の複合表現は「研究段階を経て現在active developmentにある」という経緯説明であり、現在の状態を表す語は"Active Development"の方であると解釈する。EN原文"Research Stage: Active Development"およびJP原文「研究開発段階」の両方をaliasとして記録する
- 選択肢B: 正規表記を"Research"とする。JP版「研究開発段階」の「研究」という語を重視し、現時点ではまだResearch段階にあると解釈する。EN原文・JP原文をaliasとして記録する
- 選択肢C: 現時点では正規表記を選定せず、複合表現である事実そのものを記録するにとどめ、m-sirius-k本人(博士)に実際の状態を直接確認してから選定する

### 支持根拠・反証

| 選択肢 | 支持根拠 | 反証 |
|---|---|---|
| A | 7段階語彙は英語表記で定義されており、EN版の末尾に置かれた"Active Development"は現在の状態を表す語として自然に読める語順にある | JP版に対応する語が存在しないため、EN版の解釈がJP版の意図と一致するかは未確認 |
| B | JP版「研究開発段階」の「研究」を字面どおり読めば"Research"に近い | EN版がわざわざ"Research Stage:"という接頭辞をつけた上で"Active Development"と明記しており、単純な"Research"のみとは考えにくい |
| C | EN/JP間の不一致という事実自体が、本人による確認なしに機械的推測で正規化することのリスクを示している | Decision Rule Layer類型1の裁定の中身は「正規表記を1つ選び、他はaliasとして記録するだけ」であり、意味論的判断を要しないと定義されている。選択肢Cは類型1の枠組みでは判定を先送りすることになる |

### くろこの推奨(提案)

選択肢Aを推奨する。理由: 複合表現の語順(先に"Research Stage"、後に"Active Development")から、後者が現在の状態を表すという読み方が最も自然であり、7段階語彙のいずれか一つに正規化するという類型1の要請にも適合する。ただし、これは提案であり、最終選定は博士が行う。

## 第2部: 類型2(構造問題) - Active/Active Development混在(Ambiguity-1)の語彙体系上の扱い

対象: mocka-civilization/mocka-external-brain/mocka-transparency/MoCKA-KNOWLEDGE-GATEの4リポジトリ(いずれもREADME表記は"Active Development"だが最終push 96日前で同一タイムスタンプ)。個別リポジトリの最終的な位置づけ選定はTask-I(SATELLITE_REPOSITORY_POSITIONING_OPTIONS_v0.1.md)で既に選択肢が整理されており、QUEUE-2で扱う。本節では、この事例が7段階語彙という体系そのものに新規段階の追加を要求するものかどうかを扱う。

### 選択肢

- 選択肢A: 新規段階は追加しない。7段階語彙は自己申告の状態区分であり、更新頻度(最終push日時)は別軸の観測指標として扱う。既存の"最終push"列で十分に表現できているため、語彙自体を複雑にする必要はない
- 選択肢B: 新規段階を追加する。"Active Development"と"Stable"の間に、自己申告はActiveだが一定期間(閾値は別途要確定)更新がない状態を示す中間段階を設ける(名称は仮に"Dormant"、確定は博士が行う)
- 選択肢C: 段階を追加する代わりに、既存7段階に直交する「検証状態」軸(自己申告のみ/観測裏付けあり)を追加し、2軸モデルに拡張する

### 支持根拠・反証

| 選択肢 | 支持根拠 | 反証 |
|---|---|---|
| A | 今回のambiguityは「7段階のどこに位置するか分からない」のではなく「自己申告と観測事実が食い違う」という別種の問題であり、DECISION_RULE_LAYER_v1.0.mdの類型3(実装主張問題)に近い性質を持つ | 現行7段階のみでは、今回のような「自己申告と実態の乖離」が起きるたびに個別ambiguityとして扱うことになり、再発防止にならない |
| B | 乖離状態を語彙として明示できれば、今後同種の事例を機械的に分類できる | 新規段階を追加すると、7段階という前提(REPOSITORY_STATUS_VOCABULARY_v0.1.mdで「博士から提示された7段階を基本形とする」と明記済み)を変更することになり、影響範囲が本節の裁定を超える |
| C | 段階数を増やさずに情報を追加でき、7段階という前提を維持できる | 2軸モデルはA・Bより設計変更の規模が大きく、実装(表示・記録フォーマット)への影響も本節の範囲を超える可能性がある |

### くろこの推奨(提案)

選択肢Aを推奨する。理由: 今回の事例は語彙の粒度不足ではなく、自己申告と観測事実という異なる情報源の食い違いであり、これは類型3(実装主張問題)が扱う性質に近い。7段階という前提を変更する選択肢B・Cは、本節の裁定範囲を超える設計変更を伴う。ただし、これは提案であり、最終選定は博士が行う。

## 第3部: 類型4(モジュール境界問題) - sirius-lab二重体系(Ambiguity-3)の裁定

対象: sirius-labにはリポジトリ単位のStatus節が存在せず、製品ごとにLIVE/IN DEV/RESEARCH/COMING SOONという7段階語彙とは別の4段階体系が使われている。

### 選択肢

- 選択肢A(統合): sirius-lab側の4段階を廃止し、7段階語彙に一本化する。対応案: LIVE≒Active、IN DEV≒Active Development、RESEARCH≒Research、COMING SOON≒対応なし(新規段階が必要)
- 選択肢B(意図的並行・境界明示による共存): 7段階語彙は「リポジトリ単位」、sirius-labの4段階は「製品単位」という異なる粒度の語彙として、両方を制度上正式に認める。7段階語彙はGitHubリポジトリのStatus節にのみ適用し、sirius-lab配下の個別製品表記には適用しないと境界を明示する
- 選択肢C(凍結): 判定を保留する。再検討条件: sirius-lab-productsのREADME本文取得が完了した時点、またはsirius-lab配下の製品数が一定以上に増えた時点で再検討する

### 支持根拠・反証

| 選択肢 | 支持根拠 | 反証 |
|---|---|---|
| A | 単一語彙での運用は監査・比較を容易にし、Decision Rule Layer自体が目指す「判定語の混用防止」という目的と方向性が一致する | REPOSITORY_STATUS_VOCABULARY_v0.1.md第2部の備考で、sirius-labは「対象がリポジトリでなく製品単位のため対応不能」と既に記録されている。対象の粒度が異なるため、強制的な対応付けは複数製品を含むリポジトリの状態を単一ステータスに圧縮し、情報を失う恐れがある |
| B | 対象の粒度が実際に異なる(リポジトリ vs 製品)という観察事実に最も忠実であり、無理な統合による情報損失を避けられる | 二つの語彙体系が並存すると、将来の監査で「このrepoは対応不能」という事例が増え続ける可能性があり、境界の運用ルールを明文化するコストがかかる |
| C | sirius-lab-productsのREADME本文が未取得(第5部の未確定事項、REPOSITORY_STATUS_VOCABULARY_v0.1.md)であるなど、判定材料がまだ不足している | 判断材料の不足は「製品単位語彙の存在自体」を否定する材料ではなく、凍結の理由としては弱い可能性がある。他のambiguity(第1部・第2部)との整合的な処理が遅れる |

### くろこの推奨(提案)

選択肢Bを推奨する。理由: 対象の粒度(リポジトリ/製品)が異なることは既にTask-Hで観察事実として確認されており、選択肢A(統合)は情報損失のリスクが具体的に指摘できる。選択肢C(凍結)の根拠は「sirius-lab-products README未取得」という一点のみであり、製品単位語彙の存在自体を疑う材料ではない。ただし、これは提案であり、最終選定は博士が行う。
