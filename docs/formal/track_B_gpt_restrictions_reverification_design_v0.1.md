# GPT_RESTRICTIONS.md 自動更新 - 再検証ステップ設計案 v0.1

## 0. 本文書の位置づけ

Track B改善タスク(2)。DC_20260730_003で記録された未解決点(2)"GPT_RESTRICTIONS.mdの自動更新機構に再検証ステップを追加すべきか"への対応として、設計案を複数提示する。

本文書は設計案の提示のみであり、実装コードは含まない。既存ファイル(GPT_RESTRICTIONS.md、tools/mocka_restrictions.py、tools/mocka_risk_engine.py等)への変更は一切行っていない。Decision Ledgerへの書き込みも行っていない。

Track A理論上の位置づけ: pDERS_sound_local_approximation_v0.1.md のLemma S2(Update Monotonicity)が示した非対称性 - weakening updateでは既存の証明・承認が自動的に保持されるが、strengthening updateではそれが保証されない - が本調査の出発点である。GPT_RESTRICTIONS.mdの自動更新は禁止事項を追加する方向の更新、すなわちstrengthening updateに該当する。

## 1. Current Auto-Update Flow(現状調査、根拠つき)

読むだけで変更は一切行わず、以下のファイルを調査した: `tools/mocka_restrictions.py`、`tools/mocka_risk_engine.py`、`docs/incidents/INC-20260401-001.md`、`docs/incidents/INC-20260401-002.md`、現行の`docs/governance/GPT_RESTRICTIONS.md`。

### 1.1 実際の更新チェーン

自動更新は以下の一連の処理として実装されている(すべて`tools/mocka_risk_engine.py`内、`update_events_risk()`関数、113-160行)。

1. `data/events.csv`の各行についてリスク判定を行う(`assess_risk()`、24-66行)。`error_rate`の数値、または`ERROR`/`429`/`CRITICAL`等のキーワードに基づき`risk_level`を`normal`/`MEDIUM`/`HIGH`/`CRITICAL`に分類する。
2. `risk_level`が変化し、かつ判定結果が`CRITICAL`または`HIGH`であり、かつ同じevent_idに言及する既存INCファイルが無い場合、`auto_generate_incident()`(75-111行)が新規`docs/incidents/INC-{日付}-{連番}.md`を**自動生成**する。このとき生成される内容は、決め打ちのテンプレートであり、"## 再発防止"欄には固定文字列"(要分析)"、"## 承認"欄には固定文字列"自動生成 / 要Claude確認"がそのまま書き込まれる(89-107行)。すなわちこの時点では人間による分析も承認も行われていない。
3. 同じ`update_events_risk()`呼び出しの中で、新規INCが1件でも生成されていれば、直後に`os.system(f"python {RESTRICTIONS}")`が実行される(154-156行)。これは`tools/mocka_restrictions.py`をサブプロセスとして即座に呼び出す処理であり、INC生成と同一の実行フロー内で、人間の介在なく連続して発生する。
4. `tools/mocka_restrictions.py`の`generate_restrictions()`(8-58行)は、`docs/incidents/`配下の**全INC-*.mdファイル**を毎回スキャンし、各ファイル中の"## 再発防止"見出し以降・次の"##"見出しまでのテキストをそのまま抽出する(15-19行)。この抽出処理には、内容が実際に分析済みか、"## 承認"欄が何であるかを確認するロジックは一切存在しない。抽出したテキストをそのまま結合し、`docs/governance/GPT_RESTRICTIONS.md`を**全文上書き**する(52-53行、追記ではなく毎回の完全再生成)。

### 1.2 実データによる裏付け

`docs/incidents/INC-20260401-002.md`を確認したところ、"## 再発防止：\n(要分析)"というプレースホルダがそのまま残っている(自動生成後、分析が完了していない状態)。

現行の`docs/governance/GPT_RESTRICTIONS.md`(セッション冒頭で読み込み済み)には、これに対応する"### INC-20260401-002 より\n:\n(要分析)"という一節がそのまま含まれている。

これは、未分析のプレースホルダテキストが、GPTへの指示書冒頭で毎回参照される"公式の"禁止事項ファイルに、実際にそのまま反映されてしまっている事実を示す。理論上想定されていたリスク(strengthening updateが未検証のまま反映される)が、実データにおいて既に発生していたことを裏付ける具体例である。

一方、INC-20260401-001.mdは"## 再発防止"欄に具体的な3項目(憲章第2条制定、secrets/フォルダ運用開始、.gitignore完全版適用)が記載されており、"## 承認：Claude Sonnet 4.6 / 2026-04-01"という人間(エージェント)による承認記録も存在する。ただし、この承認記録もまた`generate_restrictions()`側では一切参照されておらず、"## 承認"欄の有無・内容にかかわらず"## 再発防止"欄のテキストが機械的に抽出される点は変わらない。

### 1.3 調査の限界(正直な報告)

`tools/mocka_risk_engine.py`が実際にどの頻度・どのトリガー(定期実行/手動実行/他プロセスからの呼び出し)で動作しているかは、本リポジトリ内では確認できなかった。ファイル末尾は`if __name__ == "__main__":`という手動実行用のエントリポイントのみであり、本リポジトリ内にはこれを自動起動するcron設定・スケジューラ設定・フック定義は見つからなかった(該当拡張子ファイルを検索したが該当なし)。

これは"自動実行の仕組みが存在しない"ことの証拠ではない。原本環境(パス表記`C:\Users\sirok\MoCKA\...`から見て、Windows環境上の元リポジトリ)側でタスクスケジューラ等により定期実行されている可能性は、本調査の範囲(このLinuxクローン上のファイル調査)からは確認も否定もできない。この点は判定不能として明記する。

## 2. Design Candidates(設計案、最低2案、各案の仕組みとトレードオフ)

くろこ実行指示書に例示された(a)(b)(c)に加え、現状調査で見つかった既存だが未活用の"## 承認"欄を土台にした(d)を加え、計4案を提示する。優劣・推奨は付けない。

### 案(a): 次回実行前の人間承認必須化(Pre-execution Gate)

仕組み: `generate_restrictions()`による`GPT_RESTRICTIONS.md`の再生成そのものは即座に行うが、GPT_RESTRICTIONS.mdに"未承認"の禁止事項が含まれる場合、次にGPTエージェントが実行される前に人間(きむら博士またはClaude R02)による承認を必須のブロッキングステップとして挟む。承認されるまで該当GPTセッションの起動自体を止める、あるいは起動時に警告を強制表示する。

トレードオフ:
- 利点: strengthening updateが未検証のまま実運用に反映される事態を機械的に防げる。Lemma S2のリスクをほぼ解消できる。
- 欠点: インシデント対応の迅速性という自動更新機構の本来の目的と正面から衝突する。CRITICAL判定された直後に、その場でGPTの動きを縛りたい(禁止事項を即座に効かせたい)場合、人間の承認待ちで遅延が生じるため、"迅速な対応"という目的そのものを損なう可能性がある。承認者(きむら博士)が不在・多忙な場合、GPT作業全体が停止するリスクもある。

### 案(b): 即時反映+期限内レビュー必須+未レビュー時自動ロールバック(Reflect-then-Verify with Rollback)

仕組み: 自動更新は現状通り即座に反映する(迅速性を維持)。ただし、反映と同時に"未検証"のフラグを該当禁止事項に付与し、一定時間(例: 24時間、48時間等、要検討)以内に人間レビューが行われなければ、その禁止事項のみを自動的にロールバック(GPT_RESTRICTIONS.mdから除去、または明示的に無効化)する。

トレードオフ:
- 利点: 迅速な対応という目的を損なわない(即座に効く)。かつ、レビューされないまま無期限に禁止事項が居座り続けることも防げる。
- 欠点: ロールバックの実装自体が新たな複雑性・新たな障害点を持ち込む(ロールバック処理自体にバグがあれば、意図せず正当な禁止事項まで消える可能性がある)。また、レビュー期限内に危険な状況が実際に発生した場合、"反映されてから消えるまでの間"は未検証のまま効いているため、Lemma S2のリスクを完全には解消しない(緩和に留まる)。期限をどの程度に設定するかという新たな調整パラメータが増える。

### 案(c): 更新強度による分類(Severity-Tiered Approval)

仕組み: 更新の"強度"を分類し、軽微な更新(例: 既存の"常時禁止"リストへの単純な追加、影響範囲が限定的なもの)は自動反映を許容する一方、重大な更新(例: 既存の禁止事項の削除・弱体化、広範なエージェント行動への影響を伴うもの)にのみ人間承認を要求する。

トレードオフ:
- 利点: 大半の更新(軽微なもの)については迅速性を維持しつつ、リスクの高い変更にのみ人間の目を通す、費用対効果のバランスを取れる。
- 欠点: "強度"の分類基準そのものの設計が新たな難所になる。分類ロジックが甘ければ、実質的に案なしと変わらない(すべてが"軽微"に分類されてしまう)。分類ロジックが厳しすぎれば、実質的に案(a)と変わらない(すべてが人間承認待ちになる)。現状のGPT_RESTRICTIONS.mdの生成ロジック(全INCの再発防止欄を機械的に結合するのみ)には、そもそも"新規追加分"と"既存分"を区別する仕組みが無く、この案の実装には現状のgenerate_restrictions()自体の設計変更が前提になる。

### 案(d): 既存の"承認"欄を実効的なゲートに昇格させる(Approval-Field Enforcement)

現状調査で判明した通り、INC-*.mdには既に"## 承認"欄が存在し、自動生成時には"自動生成 / 要Claude確認"という値が入る(未承認を示す既存の記述慣行)。しかし`generate_restrictions()`はこの欄を一切参照していない。

仕組み: `generate_restrictions()`が各INCファイルを読む際、"## 承認"欄の値を確認し、"自動生成 / 要Claude確認"のような未承認を示す値のままである場合は、その"## 再発防止"内容をGPT_RESTRICTIONS.mdの正式な禁止事項一覧には含めず、別枠の"未検証・レビュー待ち"セクションに分離して記載する(GPTへの拘束力は持たせない、または警告表示のみに留める)。承認欄が具体的な承認者名・日付に更新された時点で、初めて正式な禁止事項一覧に昇格する。

トレードオフ:
- 利点: 既に存在する記述慣行(承認欄)を土台にするため、新規の概念導入コストが小さい。"自動生成された直後は仮の状態であり、正式な禁止事項として扱われない"ことが明示的になり、実データで確認された"(要分析)"のような未分析プレースホルダがそのまま公式ファイルに反映される現状の問題を直接解消できる。
- 欠点: CRITICAL判定された直後の危険な状況に対し、"仮の状態"のままでは実効的な拘束力を持たない期間が生じるため、案(a)と同様に迅速な対応という目的とのトレードオフが生じる。また"レビュー待ち"状態が放置され続けた場合、案(b)のような自動失効の仕組みが無ければ、無期限に未検証状態が積み上がるリスクがある(案(b)との組み合わせが自然に検討されうるが、それは本文書の評価対象外の複合案である)。

## 3. Evaluation against Lemma S2 and Incident-Response Speed

各案が、Lemma S2の指摘するリスク(strengthening updateが未検証のまま反映される)をどこまで軽減し、インシデント対応の迅速性をどれだけ犠牲にするかを、断定的な優劣づけを避けつつ整理する。

| 案 | Lemma S2リスクの軽減度合い | 迅速性への影響 |
|---|---|---|
| (a) 事前承認必須 | 高い(反映前に必ず人間の目が入るため、未検証反映は原理的に発生しない) | 大きい(承認待ちの間、禁止事項が一切効かない空白期間が生じる) |
| (b) 即時反映+期限内レビュー+自動ロールバック | 中程度(反映から失効までの間は未検証のまま効いてしまう、緩和はできるが解消はできない) | 小さい(反映自体は即時) |
| (c) 強度による分類 | 分類基準の設計次第で変動(基準が甘ければ(b)より弱く、厳しければ(a)に近づく、両端の間で連続的に変化する) | 分類基準の設計次第で変動(軽微側は小さい、重大側は(a)相当) |
| (d) 承認欄の実効ゲート化 | 高い(正式反映を承認欄の状態に紐づけるため、未承認のプレースホルダがそのまま公式ファイルに混入する現状の実例は解消される) | 大きい(未承認の間は正式な拘束力を持たない点は(a)と同様の性質) |

いずれの案も、Lemma S2が示す"weakening updateは自動継承されるがstrengthening updateはされない"という非対称性を完全に解消するものではなく、それぞれ異なる形で緩和するに留まる。特に(b)は迅速性を優先する分だけリスク軽減が部分的であり、(a)(d)はリスク軽減を優先する分だけ迅速性を犠牲にするという、本質的なトレードオフの構造がある。(c)はこの2軸の間のどこに着地するかが分類基準の設計に完全に依存しており、それ自体が独立した設計課題になる。
