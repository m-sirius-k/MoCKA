## 0. 総括

TASK-1〜6を通じて一貫して観測されたパターンは1つである。

**MoCKAには、記録（Ledger/Event）・判定（Gate/Checker）・設計（制度文書）という
「部品」は既に複数存在するが、それらを一つの正式な状態遷移として繋ぐ
「接続契約（State Transition Contract）」が制度として定義されていない。**

これは監査官R01がTASK-6裁定で示した整理と一致する。個々の欠陥（IC_20260708_004等）は
独立したバグではなく、この上位の接続契約不在から必然的に生じる症状である。
本報告はこの状態を、部品単位（A章）・遷移単位（B章）・具体的失敗例（C章）の
3つの解像度で可視化する。

## B. State Transition監査

指示書がいう理想的な状態遷移「Intent → Decision → Approval → Execution → Verification →
Seal → Completion」を、TASK-1〜6で確認した実例に当てはめる。

| 遷移 | 誰が変更可能か | Checkerは存在するか | Ledgerは残るか | Human Gate条件はあるか |
|---|---|---|---|---|
| Intent → Decision | 任意（AI/システム、明文の権限制御なし） | なし | 該当イベント次第（AUTO_SEAL_PENDING等は記録あり） | なし |
| Decision → Approval | GL7（機械的dry run）、`_auto_approve_prevention()`（severity閾値）、Review Gate（人間HTTP呼出）の3経路が並立 | GL7は「機械的検査のみ」と自己限定。Review Gateのみ実質的なapprove()呼出を要求 | GL7: event_bus転送のみ。`_auto_approve_prevention()`: **なし**。Review Gate: human_gate_eventsテーブルにあり | Review Gateのみあり（fail-closed設計、TASK-2確認済み）。他2経路はなし |
| Approval → Execution | SealGovernanceGateが自動実行。`human_gate_override_event_id`があれば無検証で実行 | なし | Decision Ledger記録あり（ただし承認主体が`system:seal_governance_gate`というシステム名義） | **名目のみ**。実質的な検証なし（IC_20260708_004） |
| Execution → Verification | `mocka_git_safe_commit()`のpost_commit検証（TODO_426是正済み） | 機械的検証（post_commit_violation）はあり | あり | 該当なし（機械的段階） |
| Verification → Seal | anchor_update.py / calc_summary_hash.py | なし | anchor_record.json更新+commit | なし |
| Seal → Completion（TODO完了扱い） | `mocka_update_todo(status="完了")`を呼べる任意のAIセッション | **なし（TASK-5最重要発見）** | completed_atのみ、成果物実在確認なし | **なし** |

**総括: 7遷移中、Human Gate条件が実質的に機能しているのはReview Gate（Decision→Approval間の
一部）のみである。Seal→Completion（TODO完了）に至っては、Checker・Ledger内容確認・
Human Gateのいずれも存在しない、本監査系列で発見した中で最も検証の薄い遷移である。**

## I. 結論・Phase 1移行への申し送り

TODO_370/371の監査結論確定を待つ間の「地ならし」として、以下が確定できた。

1. **最優先で扱うべき既存ギャップは2つ**: `/audit/seal`のHuman Gate未接続（IC_20260708_004、
   現行の開いた経路）と、`mocka_update_todo`の無検証完了扱い（TASK-5、C分類候補）。
   いずれも「新設」ではなく「既存の接続不備の是正」である。
2. **Gate三値化・HOLD実装の土台は既に存在する**: `phi_os/human_gate.py`のPENDING状態機械を
   GL7の後段に接続する設計（TASK-2 4章）が、新規状態機械を増やさない現実的な選択肢として
   有力である。
3. **Execution Manifestは統合が先、拡張は後**: 3系統の並立（TASK-3）を解消しないまま
   新フィールドを追加すると、TASK-2で懸念した「4系統目」を生むリスクがある。
4. **Autonomy Ladderは確定分類の材料がまだない**: 実績要件の定義自体が存在しないため
   （TASK-4 2章）、L0〜L5への確定分類はTODO_370/371の結論を待つべきという指示書v2の
   方針は本調査でも裏付けられた。
5. **Writer/Checker設計は「発掘」で足りる**: 新設ではなく、既存のWRITER_CHECKER_
   INSTITUTIONAL_DESIGN_v0.1.mdの再評価・接続を優先すべきである（TASK-6）。

TODO_370/371の監査結論が確定した時点で、本報告のA〜G章を突き合わせることで、
制度設計（Phase 1）へ即座に移行できる状態にあると判断する。
