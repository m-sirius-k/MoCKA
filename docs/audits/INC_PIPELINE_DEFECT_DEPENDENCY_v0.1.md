## 3. Root Cause Analysis

### 3.1 RC-A: data/events.csv のencoding契約の不在

D-4は"CSVが壊れている"問題ではなく、"同一の共有ファイルに対して、相反する
encoding規約を持つ全文書換え主体が複数存在する"問題である。

コード上の根拠(Confirmed):

| 主体 | 位置 | モード | encoding | BOMへの作用 |
|------|------|--------|----------|-------------|
| interface/db_helper.py `_ensure_csv()` | :74-79 | "w" | utf-8-sig | BOMを付ける(ファイル不在時のみ) |
| interface/db_helper.py 追記系 | :196 | "a" | utf-8-sig | 実測ではBOMを追加しない(3.3参照) |
| tools/mocka_risk_engine.py | :143 | "w" | utf-8 | BOMを消す |
| tools/mocka_repair_events.py | :45 | "w" | utf-8 | BOMを消す |

読み取り側の規約も分裂している。events.csv を参照するPythonファイルは58件
(backup/experiments含む、`__pycache__`除く)。そのうち少なくとも以下は
BOM耐性のある `utf-8-sig` で読む。

- caliber/chat_pipeline/chat_raw_ingest.py:17
- caliber/chat_pipeline/mocka_caliber_server.py:178
- caliber/chat_pipeline/mocka_chat_capture.py:56
- caliber/chat_pipeline/mocka_condense_worker.py:42
- caliber/incident_analyzer.py:34
- interface/essence_extractor.py:18,23,60
- mocka_v3_eval/append_incidents.py:18,269

一方、tools/mocka_risk_engine.py:118 と tools/mocka_5w1h.py:95 は BOM非耐性の
`utf-8` で読む。すなわち本パイプラインは、周辺モジュールで優勢な読取規約から
逸脱している側である。

RC-A の帰結として重要なのは以下である。

- D-4は"events.csvを直せば終わる"種類の欠陥ではない。書換え主体が2規約に
  分裂している限り、BOMの有無は最後に実行された主体によって反転し続ける
- したがってD-4の是正対象は、ファイルの現在値ではなく、読み書き双方の規約である

### 3.2 RC-B: INCファイルの状態モデルの不在

docs/incidents/INC-*.md は、同一ファイルが3つの役割を同時に担っている。

1. 検知記録(risk_engine.py:75-111 が生成)
2. 分析作業領域(5w1h.py:117-136 が追記)
3. 公開原本(restrictions.py:10-19 が読み取り、公開ファイルへ転記)

3つの役割が未分化であるため、以下がいずれも表現できない。

- このINCは分析が済んでいるか(-> D-2: 済んでいないものを公開してしまう)
- このINCは公開してよいか(-> D-1: 公開可否を判定する状態が存在しない)
- 再発防止情報は本文のどこにあるか(-> D-3: 生産者と消費者で位置が食い違う)

D-1/D-2/D-3は独立した3つのバグではなく、単一の設計欠落(状態モデルの不在)が
3つの異なる形で表出したものである。

### 3.3 測定によって棄却した仮説

`open(path, "a", encoding="utf-8-sig")` がファイル中間にBOMを挿入する、という
Pythonの既知の落とし穴が本件に関与している可能性を検討したが、以下により棄却した。

- 実測: 既存ファイルへ utf-8-sig 追記を行っても BOM は追加されなかった
  (出力実体 `b'a,b\n1,2\n3,4\n'`)
- 現物 data/events.csv のBOM出現位置は先頭(オフセット0)の1箇所のみ。
  ファイル中間へのBOM混入は発生していない

したがってD-4の発生源は追記経路ではなく、全文書換えまたは新規作成の経路である。

## 4. Failure Propagation

### 4.1 D-4 の伝播

D-4は2本の独立した経路へ伝播する。

```
D-4 (キーが ﻿event_id になる)
 |
 +--> 経路1: 書き戻し (risk_engine.py:147 の row.get(k,"N/A"))
 |            -> event_id 列が全132行 N/A になる (Data Destruction)
 |            -> この経路は INC が生成されたか否かに関わらず実行される
 |               (書き戻し L143-147 は L154 の分岐より前にある)
 |            -> 実測: Run A で INC 0件でも event_id は全損した
 |
 +--> 経路2: 重複判定 (risk_engine.py:132 の row.get("event_id",""))
              -> 空文字 -> D-5 の活性化
```

経路1はD-5によって遮蔽されない。すなわちD-4の実害はINC生成の有無と無関係に
発生する。これは"INCが生成されないので何も起きていない"という理解が
成立しないことを意味する。

### 4.2 D-2 と D-3 の伝播(是正組合せ表)

コード読解およびdry-run実測に基づく、4通りの是正状態と最終出力の関係。

| # | D-2 | D-3 | GPT_RESTRICTIONS.md への出力 | 根拠 |
|---|-----|-----|------------------------------|------|
| 1 | 未 | 未 | 常に `(要分析)` | 現行。Run A/B で実測 |
| 2 | 済 | 未 | 常に `(要分析)`。**改善なし** | 5w1h.py:135-136 は末尾appendのみで `## 再発防止` 欄を書き換えないため、抽出結果(restrictions.py:16-17)は不変 |
| 3 | 未 | 済 | 既存INCは反映される。**新規INCのみ1サイクル遅延** | restrictions実行時点(L155)では当該INCに5W1Hセクションが存在しない(生成はL159) |
| 4 | 済 | 済 | 単一実行内で正しい内容が出力される | - |

ケース3の"1サイクル遅延"は、実際には遅延では済まない可能性がある。
次回の再生成は `if incidents_generated:` (risk_engine.py:154) が真になるとき、
すなわち新規INCが生成されるときにしか起きないためである(4.4節 M-2)。

### 4.3 D-1 と D-2 の結合

D-1に承認ゲートが導入された場合、公開対象は"承認済みのINC"に限定される。
承認は分析完了後にしか付与されえないため、D-1の是正はD-2の症状の一部を
覆う可能性がある。ただし以下は残る。

- 承認判定が"分析完了"ではなく"承認欄の文字列"に基づく限り、分析未完のまま
  承認欄だけが埋まったINCは通過しうる
- D-2は"起動順序"の欠陥であり、D-1は"公開可否"の欠陥である。両者は
  対象が異なるため、D-1の是正はD-2を消滅させるのではなく症状を隠す方向に働く

本文書はこの結合を事実として記録するに留め、いずれを先に是正するかの判断は行わない。

### 4.4 出力の停留

```
1回目の実行で risk_level が確定値へ書き換わる (risk_engine.py:124-126)
   -> 2回目以降は row.get("risk_level") != risk が偽
   -> INC生成ブロック全体に入らない
   -> incidents_generated が空
   -> restrictions.py が起動しない (L154)
   -> GPT_RESTRICTIONS.md は永久に更新されない
```

実測(Run B 2回目): risk更新0件 / INC生成0件 / GPT_RESTRICTIONS.md は
1回目の出力とバイト一致。

## 5. Masking Analysis

| ID | 遮蔽するもの | 遮蔽されるもの | 性質 | 根拠 |
|----|--------------|----------------|------|------|
| M-1 | D-5 | D-1 / D-2 / D-3 | 完全遮蔽 | INCが1件も生成されないため下流(restrictions/5W1H)が起動しない。Run Aで実測(CRITICAL/HIGH 6件が全てSKIP) |
| M-2 | risk_level の冪等性(L124) | D-2 / D-3 の是正効果と、既存の陳腐化 | 停留による遮蔽 | 再生成の契機が新規INC生成に限られる。Run B 2回目で実測 |
| M-3 | D-2 | D-3 | 部分遮蔽 | D-3のみ是正しても新規INCは1サイクル遅延する(4.2 ケース3) |
| M-4 | D-3 | D-2 | 部分遮蔽 | D-2のみ是正しても出力は変わらない(4.2 ケース2) |

### 5.1 遮蔽の解除がもたらす状態変化

M-1が解除された時点(D-4/D-5是正時)で、それまで抑止されていたINC生成が
一斉に発火する。実測(Run B)では6件が同時生成され、そのすべてが
`(要分析)` として公開ファイルへ掲載された。

すなわち M-1 は"問題を隠している"だけでなく"解除の瞬間に実害が拡大する"
性質を持つ。この点は修正順序の比較(INC_PIPELINE_REMEDIATION_SCOPE_v0.1.md 4節)で
露出窓として扱う。

### 5.2 遮蔽されていないもの

以下はM-1の遮蔽を受けない。

- D-4の経路1(event_id列の全損)。書き戻しはINC生成の有無と無関係に実行される
- GPT_RESTRICTIONS.md に現に掲載されている `(要分析)` 1件(INC-20260401-002由来)。
  これは2026-04-01に生成済みで、origin/mainへ到達済みである

   Confirmedだが、それが現BOMの発生源であることは Hypothesis である

   この差異が判定にどう影響するかは、判定方式が確定していないため未評価

   ものである。Cloudflare Workers側、外部cron、他ホストは未走査であり、
   範囲外に別の書換え主体が存在しないことは確認していない
