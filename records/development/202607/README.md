### 3-3. Notion API エラーによる同期の全体停止

| 項目 | 内容 |
|------|------|
| スクリプト | `fix_error_handling.py` および `patch_script.py` |
| 問題 | 1件の投入が API エラーになると例外が伝播し、同期処理全体が止まっていた |
| 修正 | `notion_post` 呼び出しを try/except で包み、失敗した件は `[SKIP]` を出力して `False` を返し、後続の処理を継続する |
| 現状 | **反映済み**。`[SKIP` を含む分岐が現在のファイルに存在することを確認 |

`fix_error_handling.py` と `patch_script.py` は**同一の目的に対する2つの実装**である。
前者は文字列置換、後者は行単位の走査で同じ try/except を挿入する。
どちらが最終的に適用されたかはスクリプトからは判別できないが、
結果として現在のファイルには try/except が入っている。
**2つの手法を試した記録**として両方を残す。

## 4. 修正理由(なぜこの形になったか)

3-1 から 3-3 はいずれも"**同期が途中で止まる、または不完全な結果になる**"問題である。

同期処理は多数のレコードを順に投入するため、1件の失敗で全体が止まると、
どこまで成功したのかが分からなくなる。
そのため修正の方向は一貫して"**失敗を検知しつつ処理を継続し、失敗箇所を出力する**"ことに向いている。

3-2 の `parse_date()` が判定不能時に `None` を返してプロパティ自体を設定しない設計も同じ思想で、
**不確かな値を書き込むより、書き込まないことを選んでいる**。

## 5. 再発防止の観点

このディレクトリが示す教訓は3点ある。

### 5-1. 修正を作業ツリーに置いたまま commit しない期間が長かった

2026-07-22 の修正が commit されたのは 2026-07-31 である。
9日間、修正内容は git 履歴に現れず、本スクリプト群だけが唯一の記録だった。
**検証済みの修正は、その時点で commit する**必要がある。

これは MoCKA が既に運用ルール化している事項でもある
(`.claude/CLAUDE.md`"CHANGE_DONE記録後は、次の操作に進む前に、
該当変更を必ず正しいリポジトリへcommitする")。

### 5-2. ソースファイルを書き換えるスクリプトは再実行できない

`fix_ids.py` / `fix_date.py` / `fix_error_handling.py` / `patch_script.py` は
`interface/mocka_notion_sync.py` を読んで書き戻す。

**現在これらを再実行してはならない。**

- 置換対象の文字列は既に置換済みであり、一致しない
- `patch_script.py` は行の内容で判定するため、二重適用や不正な挿入が起こりうる
- いずれも変更前のバックアップを取らない

再実行が必要な状況が生じた場合は、対象ファイルの現在の内容を確認し、
スクリプトを流用せず個別に判断すること。

### 5-3. 同一目的のスクリプトが2つ存在した

3-3 の修正に対して `fix_error_handling.py` と `patch_script.py` の2実装がある。
どちらが適用されたかがスクリプト側に残っていないため、
後から経緯を再現するには現在のファイル内容と突き合わせる必要がある。

修正手法を切り替えた場合は、**採用しなかった側をその場で明示する**と追跡が容易になる。
