## CURRENT ARCHITECTURE

### Overall Data Flow

```
Human Input
    |
    v
[PHI-OS Human Gate] OR [Jarvis HumanGate]
    |
    +---> mocka_events.db (Event Store)
    |
    +---> [LedgerAdapter] (test-only)
            |
            v
        jarvis_ledger.jsonl
    
    +---> [MCP Server] (direct)
    |
    v
decision_ledger.jsonl
    |
    v
[SealGovernanceGate] (direct)
```

### Three Parallel Systems

| System | Primary Storage | Authority Source | Human Gate Connected? | Canonical? |
|--------|-----------------|-----------------|----------------------|-----------|
| **Event Store (PHI-OS)** | mocka_events.db | Approver name (unverified) | YES (production) | NO |
| **Decision Ledger** | decision_ledger.jsonl | MCP client (unverified) or GL7 (pre-execution) | NO | NO |
| **Test Ledger (Jarvis)** | jarvis_ledger.jsonl | Hardcoded "HUMAN_GATE" | NO (test-only) | NO |

## DETAILED BOUNDARY ANALYSIS

### 1. Human Gate Approval Generation Point

**Production Path (PHI-OS)**:
```
Location: phi_os/human_gate.py:approve()
Entry: HTTP POST /human_gate/approve
Input: request_id, approver
Process:
  - Query: _latest_event(conn, request_id)
  - Validation: PENDING → APPROVED state transition
  - Generation: event_id = _next_event_id() [HG20260813_NNNNNNNNN{hex}]
  - Write: INSERT INTO human_gate_events
  - Authority: approver parameter (unverified caller-provided)
Storage: mocka_events.db.human_gate_events
Output: {"request_id": ..., "status": "APPROVED", "event_id": ...}
```

**Test Path (Jarvis)**:
```
Location: runtime/jarvis/gate/human_gate.py:approve(decision_id)
Entry: Method call (in-memory)
Input: decision_id
Process:
  - Create DecisionRecord(decision_id, status="APPROVED")
  - Call LedgerAdapter.record()
Authority: Hardcoded actor = "HUMAN_GATE"
Storage: jarvis_ledger.jsonl (via LedgerStore)
Output: Record dict
```

**Comparison**:
- PHI-OS: Authority = caller-supplied name (unverified)
- Jarvis: Authority = hardcoded string (not individual)
- **No Authority Verification in Either Path**

### 2. Approval Information Retention Format

**PHI-OS Event Record**:
```json
{
  "event_id": "HG20260813_001ABC123DEF",
  "timestamp": "2026-08-13T10:30:45.123456Z",
  "type": "human_gate_request",
  "action": "approve",
  "request_id": "REQUEST_20260813_001",
  "payload": "{}",
  "previous_state": "PENDING",
  "next_state": "APPROVED",
  "approver": "john_doe"  [unverified, caller-supplied]
}
```

**Storage**: SQLite in mocka_events.db (mutable, event-sourced, queryable)

**Jarvis Decision Record**:
```json
{
  "decision_id": "DC_20260813_001",
  "status": "APPROVED",
  "actor": "HUMAN_GATE",  [hardcoded, not individual]
  "timestamp": "2026-08-13T10:30:45.123456Z"
}
```

**Storage**: JSONL in jarvis_ledger.jsonl (append-only, immutable, in test file)

**Key Difference**: 
- Event Store: **Mutable, state-based, per-approver identity**
- Decision Ledger: **Immutable, record-based, generic actor**

### 3. Decision ID Generation Point

**PHI-OS**: Does NOT generate decision_id
```
- Human Gate works with request_id (generated by requestor)
- No decision_id created by Human Gate
- No connection between request_id and decision_id
```

**MCP Server**: Generates decision_id
```
Location: mocka_mcp_server.py:_next_decision_id()
Format: DC_YYYYMMDD_NNN [example: DC_20260813_001]
Owner: MCP Server (not Human Gate)
Integration: No link to Human Gate approval
```

**Jarvis**: Uses external decision_id
```
- Caller provides decision_id
- HumanGate.approve(decision_id) creates record with that ID
- No generation, only recording
```

**Critical Gap**: 
- **PHI-OS Human Gate approval uses request_id (internal)**
- **Decision Ledger entries use decision_id (MCP-generated)**
- **NO MAPPING BETWEEN THEM**

---

### 4. Event Store Write Path

**PHI-OS Human Gate → mocka_events.db**:

```
phi_os/human_gate.py:approve(request_id, approver)
  |
  ├─ State transition validation
  │   └─ _latest_event() reads previous state
  │
  ├─ Event record construction
  │   ├─ event_id = _next_event_id()
  │   ├─ timestamp = _now_iso()
  │   ├─ request_id = input
  │   ├─ approver = input [UNVERIFIED]
  │   ├─ action = "approve"
  │   └─ next_state = "APPROVED"
  │
  └─ Persistence
      └─ conn.execute(INSERT INTO human_gate_events (...))
         └─ mocka_events.db
```

**Write Guarantees**:
- ✅ Duplicate prevention (by request_id lookup)
- ✅ State transition enforcement
- ❌ Authority verification (approver parameter trusted)
- ❌ Immutability enforcement (SQLite allows updates)
- ⚠️ Queryable (SQL index possible, but event-sourced)

**No LedgerAdapter Involvement**

---

### 5. Decision Ledger Write Path

**Path A: MCP Direct Write**:
```
mocka_mcp_server.py:mocka_decision_write(decision_id, title, ...)
  |
  ├─ Zero validation
  ├─ Zero authority check
  ├─ Zero Human Gate check
  |
  └─ _append_decision(record)
      └─ open("data/decisions/decision_ledger.jsonl", "a").write(json.dumps(record) + "\n")
          └─ File-level append-only
```

**Guarantees**:
- ✅ Append-only (file "a" mode)
- ✅ Immutable (once written, cannot modify)
- ❌ Duplicate prevention (any MCP client can write same decision_id)
- ❌ Authority verification (unverified approver field)
- ❌ Human Gate connection (zero check)

**Path B: SealGovernanceGate Direct Write**:
```
governance/seal_governance_gate.py:execute()
  |
  ├─ GL7 governance check (BEFORE execution)
  ├─ Seal script execution
  |
  └─ _record_decision_unit()
      ├─ DecisionRecord(decision_id, ..., actor="system:seal_governance_gate")
      |
      └─ open("data/decisions/decision_ledger.jsonl", "a").write(...)
          └─ decision_ledger.jsonl
```

**Guarantees**:
- ✅ Pre-execution authority (GL7 check before operation)
- ✅ Append-only (file "a" mode)
- ✅ Immutable (once written)
- ❌ No re-verification at write time
- ❌ Human Gate connection (zero involvement)

**Key Finding**: Both paths write directly, bypassing any intermediate boundary.

### 6. LedgerAdapter Usage Points

**Current Usage**:
```
Only in: runtime/jarvis/gate/human_gate.py
         tests/jarvis/test_ledger_adapter.py
         
NOT in:  mocka_mcp_server.py
         governance/seal_governance_gate.py
         phi_os/human_gate.py (production Human Gate)
```

**LedgerAdapter Call Chain**:
```
HumanGate.approve(decision_id, status)
  |
  └─ LedgerAdapter.record(decision_id, status)
      |
      ├─ DecisionRecord.to_dict()
      |   └─ actor = "HUMAN_GATE" [hardcoded]
      |
      └─ LedgerStore.save(record)
          ├─ Load existing records (read all jarvis_ledger.jsonl)
          ├─ Check for duplicate decision_id
          ├─ Skip if found (silent fail)
          └─ Append if unique
              └─ open("data/jarvis_ledger.jsonl", "a").write(...)
```

**File Mismatch**:
- LedgerAdapter writes to: **jarvis_ledger.jsonl** (test)
- Production ledger is: **decision_ledger.jsonl** (MCP/SealGov)
- **Zero overlap**

---

### 7. Direct Write Possible Paths

**Unrestricted Entry Points**:

| Path | Entry Function | Authority Check | Duplicate Prevention | File |
|------|-----------------|-----------------|----------------------|------|
| **MCP Direct** | mocka_decision_write() | ❌ NONE | ❌ NONE | decision_ledger.jsonl |
| **SealGov Direct** | SealGovernanceGate.execute() | ✅ GL7 (pre-exec) | ❌ NONE (at write) | decision_ledger.jsonl |
| **File I/O Direct** | File write (elevated access) | ❌ NONE | ❌ NONE | decision_ledger.jsonl |
| **Event Store Direct** | Direct SQL (admin access) | ❌ NONE | ❌ NONE | mocka_events.db |

**Conclusion**: Multiple direct write paths exist with no unified control point.

## MISSING BOUNDARY

### Designed Boundary (Intent)

```
Human Gate Approval
    |
    v
[Authority Verification Boundary]
    |
    +─ Verify: Approval exists
    +─ Verify: Approver is human
    +─ Verify: Decision ID matches
    +─ Verify: No duplicate
    |
    v
Decision Ledger Entry
```

### Actual Boundary (Reality)

```
PHI-OS Human Gate → mocka_events.db
                    (NOT connected to Decision Ledger)

MCP Server ──────→ decision_ledger.jsonl
                   (NO Human Gate verification)

SealGov ─────────→ decision_ledger.jsonl
                   (NO Human Gate verification)

Jarvis HumanGate → jarvis_ledger.jsonl
                   (Test-only, different file)
```

**The Boundary Does Not Exist**:
- ❌ No connection between Human Gate approval and Decision Ledger
- ❌ No shared decision_id coordination
- ❌ No unified authority model
- ❌ Three parallel systems with no integration

## EXISTING TRUST ASSUMPTIONS

### Assumption 1: "Decision Ledger contains only approved decisions"
**Status**: ❌ FALSE
- MCP clients can write any decision_id without approval
- No Human Gate check performed
- Approver field is client-supplied (unverified)

### Assumption 2: "Human Gate approval creates a Decision Ledger entry"
**Status**: ❌ FALSE
- PHI-OS Human Gate writes to mocka_events.db only
- No connection to decision_ledger.jsonl
- Jarvis HumanGate writes to jarvis_ledger.jsonl (test file)

### Assumption 3: "LedgerAdapter enforces decision boundaries"
**Status**: ❌ FALSE
- LedgerAdapter is test-only component
- Not used in production
- Production paths (MCP, SealGov) bypass it entirely

### Assumption 4: "Decision IDs are unique in production ledger"
**Status**: ❌ FALSE
- No duplicate prevention in decision_ledger.jsonl
- MCP server can write same decision_id multiple times
- Only jarvis_ledger.jsonl has uniqueness check (test file)

### Assumption 5: "Approver identity is preserved in Decision Ledger"
**Status**: ❌ FALSE
- MCP: approver field is client-supplied string (unverified)
- SealGov: actor is hardcoded "system:seal_governance_gate"
- Jarvis: actor is hardcoded "HUMAN_GATE"
- No individual human identity in Decision Ledger

## FAILURE SCENARIOS

### Scenario 1: Duplicate Decision ID in Production

**Trigger**:
```python
# Call 1
mocka_decision_write("DC_001", title="Policy A", approved_by="alice")

# Call 2 (same ID, different caller)
mocka_decision_write("DC_001", title="Policy B", approved_by="bob")
```

**Result**:
- ✅ Both written to decision_ledger.jsonl (no prevention)
- ✅ Second entry has different title/approver
- ❌ No indication of duplicate
- ❌ Ledger contains conflicting entries with same ID

**Impact**: Audit cannot determine which is "correct"

---

### Scenario 2: Approval Without Authority Verification

**Trigger**:
```python
# Human Gate approves in mocka_events.db
human_gate.approve("REQUEST_123", approver="alice")

# Meanwhile, unauthorized system writes to Decision Ledger
mocka_decision_write("DC_456", title="something", approved_by="attacker")
```

**Result**:
- Human approval: in mocka_events.db (correct channel)
- False approval: in decision_ledger.jsonl (no verification)
- No way to distinguish between them
- Both appear as "approved" decisions

**Impact**: Decision Ledger authority is compromised

---

### Scenario 3: Re-execution Without Re-verification (SealGov)

**Trigger**:
```
Execute 1: SealGov checks GL7, approves, writes to Decision Ledger
Execute 2 (Retry): SealGov checks NOT re-performed, writes again
```

**Result**:
- First write: GL7 verified
- Second write: No re-verification, but written anyway
- Same execution_id might appear twice
- Duplicate decision entries

**Impact**: Seal authority assurance reduced by retry risk

---

### Scenario 4: Silent Duplicate in LedgerAdapter (Test)

**Trigger**:
```python
adapter.record("DC_001", "APPROVED")  # First call
adapter.record("DC_001", "REJECTED")  # Second call with same ID, different status
```

**Result**:
- First write succeeds
- Second write detected as duplicate (by LedgerStore)
- **Silently rejected** (no exception thrown)
- Caller receives record object as if write succeeded
- **Caller cannot detect failure**

**Impact**: Test code assumes success when write actually failed

## SECURITY IMPACT

### High Risk

1. **Unverified MCP Decision Creation** (RISK_001)
   - Any MCP client can create decisions in Decision Ledger
   - No Human Gate approval required
   - No authority verification
   - Duplicates possible
   - **Impact**: Decision authority undermined

2. **Approver Identity Loss** (RISK_002)
   - Human Gate approvals use individual names (mocka_events.db)
   - Decision Ledger uses generic actors or client strings
   - No proof of individual approval in formal ledger
   - **Impact**: Authority cannot be verified retroactively

3. **No Unified Authority** (RISK_003)
   - Three parallel systems (Events, Decision, Test)
   - No coordination between them
   - Decisions can exist in one system but not others
   - **Impact**: Audit trail is fragmented

### Medium Risk

4. **LedgerAdapter Test-Only** (RISK_004)
   - Designed as production boundary, deployed as test utility
   - Production bypasses it entirely
   - Code debt accumulates
   - **Impact**: Architectural inconsistency

5. **Silent Failure in Duplicate Detection** (RISK_005)
   - LedgerStore silently rejects duplicates
   - No caller indication
   - Test code may not detect failures
   - **Impact**: Test coverage is false (tests pass despite failures)

6. **Pre-execution vs. Write-time Authority (SealGov)** (RISK_006)
   - GL7 check performed before execution
   - Re-verification not performed at write time
   - Retry risk exists
   - **Impact**: Authority assurance reduced over time
